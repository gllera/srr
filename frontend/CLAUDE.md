# CLAUDE.md

## Project

SRR Frontend — single-page RSS reader. Zero runtime deps. Parcel + TypeScript + plain CSS.

## Commands

`npm run dev|build|test|lint|format|format-check|smoke` — dev server, production build (`../dist/srrf/`), vitest+jsdom, ESLint, Prettier write/check, boot smoke-test (`e2e/boot-smoke.mjs`). E2e entry points: `npm run test-contract|test-browser|test-stress` (each with its own `vitest.*.config.ts`; `vitest.shared.ts` holds common config), design harness `gen-design|shoot-design`, and `serve`/`servep` (the dev CORS pack server). Prefer the root `make` wrappers.

## Architecture

> **Deep-dives live in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).** The module table below summarises every module; the ten largest rows (`data`, `nav`, `list`, `gestures`, `pager`, `picker`, `fmt`, `profile`, `sync`, `app`) were moved there verbatim and are linked from their row. Those summaries are lossy — read the companion section before editing one of those modules.

Entry: `src/index.html` → `src/styles.css` + `src/js/app.ts`. Bundler: Parcel 2. `SRR_CDN_URL` is replaced at build time: `parcel/resolve-cdn-url.js` resolves the value, `parcel/transformer-define.js` does the literal substitution in `base.ts` (it also inlines `SRR_VERSION` — `$VERSION` env, set to the tag by release.yml's build jobs, else "dev" — and `process.env.NODE_ENV`), and `parcel/optimizer-preload-db.js` injects a `<link rel="preload" … db.gz as="fetch">` into the HTML head. Resolution: env var → `cdn-url:` from `$SRR_CONFIG_INLINE` (raw YAML) → `cdn-url:` from `$SRR_CONFIG` (file path, default `$XDG_CONFIG_HOME/srr/srr.yaml`) → fallback `"."` (relative to `index.html`: with no cdn-url the store sits next to the bundle, so `PACK_BASE = new URL(".", location)` — `base.ts`; the dev server doesn't hit this fallback, `serve` sets `SRR_CDN_URL=http://localhost:3000` explicitly). The config read (the INLINE → file → default chain) is shared with the dev pack server via `parcel/srr-config.js` (`readConfigYaml`/`parseKey`).

Dependency chain: `app → {reader, menus, search-ui, pin-ui} → els` (the four extracted UI controllers and the leaf DOM-reference map — **none of them imports `app`**; whatever they need from the orchestrator arrives through their `setup()` deps or as explicit arguments, which is what keeps the graph acyclic), `nav → {seen, saved, prefetch, route}` (the four extracted nav concerns — likewise none imports `nav`; shared state travels as explicit arguments), `app → schema → keys`, `app → nav → {data, search, fmt}`, `nav → data → {idx, cache, base}`, `app → fmt → base`, `app → list → {data, nav, fmt}` (plus `list → seen` for the row-swipe read toggle **only** — the one place outside `nav` that writes a frontier, because `nav.markAllRead`/`markUnreadFrom` bake in the ACTIVE FILTER's scope while a row gesture's scope is one feed and one chron; the `FrontierScope` argument is exactly the seam ENG3 created for a caller that knows its own scope, so this is a second CALLER, never a second write path — every tally, the seen map and the undo machinery still come through `nav`), `app → picker → {base, data, nav, fmt, search}` (picker reaches `search` for its `fold` alone — the row-search matches on the SAME folded text the article index does, rather than a second normalizer), `app → dropdown → {fmt, profile}`, `app → lightbox → dropdown` (the content-image viewer, borrowing only the shared Tab trap — a pure UI module that touches no nav/data state), `app → pin`, `{app, list, pager, player} → gestures` (imports no app module — `list` reaches it only to REGISTER its two surface gestures, the pull-to-refresh action and the row swipe, `pager` only to register the reader's, never the other way, and `player` only for the `ROW_SWIPE_TRIGGER` constant, so the queue panel's own swipe commits at the list rows' distance), `app → pager → {article-view, data, els, fmt, gestures, nav}` (the reader swipe pager's DOM half; it imports neither `app` nor `reader`, so the committed step arrives as an injected callback), `{reader, pager} → article-view → {data, fmt, urlish, format.gen}` (the pure article fill BOTH article surfaces run — a leaf like `els.ts`/`urlish.ts`, taking its nodes as an `ArticleRefs` argument rather than importing `el`, which is exactly what lets a surface `index.html` never declared reuse it), `{app, nav, dropdown, picker} → sync → profile` (the cross-device sync engine over the portable profile), `{app, picker, list} → refresh → {data, nav, search}` (the live content-sync trigger module — see Key Behaviors), `{idx, data, sw, types.d} → format.gen` (generated, see below), `search → {data, cache, format.gen}` (and `list → search` for the RDR8 term highlighting alone — `matchSpans`, so the marks agree with the fold the hits were found on; search.ts stays DOM-free and hands back raw-string ranges), `sw → sw-grammar → format.gen`, `{app, nav, fmt, pin, profile, sync} → keys` (the localStorage-key constants hub), `{app, picker, fmt, profile, sync} → urlish` (the side-effect-free http(s)-URL rules hub — `URL_DENY` + validate/normalize). All in `src/js/` except `sw.ts`, which sits at `src/` (its own row below says so too), strict mode. (`nav` owns the search **filter mode**, so it imports `search`; `dropdown` no longer imports `nav` or `data` — those moved to `picker.ts`.)

**Two surfaces + two popups.** `app.ts` tracks `view: "list" | "reader"` and switches via `showList` / `showReader` (body class `srr-view-list`); the filter-picker overlay and the settings menu (below) are popups over the list, not views of their own. **Split view** (`split.ts`, ≥1000px) shows both surfaces at once instead of switching between them: the list becomes a fixed self-scrolling pane and the reader fills the rest of the page, scrolling the window. `view` survives as which pane has **keyboard focus** rather than which pane is visible, and every "can the reader be acted on" question asks `readerLive()` (split ∧ `reader.hasArticle()` ∧ a cursor) instead — `reader.hasArticle()` reads the reader's OWN state (a `painted` flag set by `render`'s article branch and cleared by every placeholder path, plus the `el.article` unhidden / no `.srr-reader-empty` invariant), because `nav.pos` is the cursor the LIST moves too (its anchor seed, its row stepping), so it routinely names an article the pane has never rendered. The flag is not belt-and-braces: `index.html` ships `.srr-reader` empty, with neither an article in it nor `.srr-reader-empty` on it, so a pure class test reads a never-painted surface as holding an article. That matters because `showList`'s split branch **unhides the host BEFORE asking** — it must, since the single-surface layout sets `hidden` on the list, so asking first put the question to a pane still marked hidden by the layout being left, answered "nothing here" for a reader holding a perfectly good article, and let the resting paint destroy it on the way back across the breakpoint. Ordering + flag together are what make both crossings non-destructive; the crossing additionally re-derives the reader chrome (`reader.reprobeReaderChrome`), because the narrow branch DISABLED prev/next and the split branch deliberately never touches them. `showList`/`showReader` still run but neither hides the other pane; with nothing open the reader shows its **resting panel** (`app.paintRestingPane` → `nav.restingState` → `reader.renderResting`) — the same directed empty state the reader shows at a dead end, Next armed off `has_right` so "Tap Next to start reading" is true — rather than leaving two thirds of the window blank under dead arrows. Its armed Next routes through `app.enterReader` for **any** article-less pane under split (`isSplit() && !reader.hasArticle()`), not just the resting one: `nav.switchFilter`'s own "not started" placeholder paints the same panel from the same `pos = -1`, and a `nav.right()` step from either lands one PAST the cursor the list pane has already seeded — opening the lane's SECOND article and marking the first read behind you. A resting paint is deliberately NOT a navigation: no surface flip, no `document.title`, no focus grab, no hash write. What they deliberately DON'T do under split is drive the reader-only toolbar state — `showList` returns before `el.prev.disabled = true`, and every hide rule is `:not(.srr-split)`-guarded, so the toolbar's prev/next/save stay on screen from the list pane and prev/next stay enabled — nor any highlight: `.srr-row-current` is re-derived by `list.refresh()` via `followCursor()`. Opening an article from the list brings the list along instead of replacing it: every reader-pane step (arrow keys, the pager, a picker pick) calls `list.followCursor()` to re-derive the highlight and scroll the cursor row into the pane's live band. Opening the article the pane ALREADY holds is a focus change, not a render — one door (`app.openArticle`) shared by Escape and the row tap, since two affordances for one act answer it differently unless they share a body; it re-renders only when the mounted chron and the cursor both name something else, and it still `nav.publishHash()`es + `persistHash`es, because the URL is what a copied link shares and what a reload restores from (skipping it left Escape, Escape, reload landing on an empty resting pane). Two panes also mean two paints of ONE ★ set on screen at once, so the toggle crosses the seam in both directions: the reader's save button additionally `list.refresh()`es (stars, aria, and the ★ Saved lane's removal of a row un-saved from the reader — the "drop it on the way back" path, which under split has no way back), and a row's own star announces itself through the injected `list.setSavedSink` so the button re-derives when it is describing that article. The READ half is the same seam: a row swipe's mark-read moves the frontier the pane's pending pill and the tab's unread badge are derived from, and `list.refresh()` re-derives only the ROWS — so it announces through the injected `list.setFrontierSink` (→ `reReadReader` + `syncUnreadBadge`), the reconciliation `menus.afterFrontierMove` already gives every other frontier gesture. Deep-linking straight to `#pos` builds the list pane beside it through that same seam, NOT through `route()`: its numeric-position branch deliberately makes no list call, because `guard()`'s render path already runs `followCursor()`, whose not-yet-built fallback is `show(true)`. The phone-only touch gestures — toolbar auto-hide, pull-to-refresh, and the pager drag — stand down under `body.srr-split` (three class checks in `gestures.ts`, not an import, since a permanent two-pane chrome has nothing to hide, no overscroll edge to pull from, and nothing to clip a reader slide off the list pane); the hash grammar is unchanged (`#pos!tokens` addresses both panes; a `#!tokens` hash leaves the reader pane RESTING only before the session's first article, and after the first open both panes stay live, so browser-back to a list hash keeps the article beside the list exactly as Escape does; `split.e2e.test.ts` pins that contract). Keyboard: with a live pane the reader keymap runs from BOTH surfaces (`readerSteppable`) — ←/→ step the article the toolbar's ‹ › beside them step, since under split the row cursor IS the reader's article; the list's own row stepping (`list.moveSelection`) is what stands down there, and the filter-cycle keys stay on the list path (`onCycle`). Two more `view`-shaped gates became layout questions: `refreshAfterStore` runs BOTH halves under split (the pane's `onStoreGrown` used to be skipped while you read — the always-visible list silently ignored whole fetch cycles), and `refreshAfterMerge`'s gentle rebuild likewise (its "a display:none list would pin zero row heights" reasoning does not hold when the list is on screen). The **list** (`list.ts`) is home: a scannable headline feed under the current filter, newest-first, **source-keyed** — each row carries a per-feed color rail + a colored mono "source · age" eyebrow over the title (`fmt.srcColorIndex` → `data-src`; read/unread shows as title weight/brightness + rail saturation, no separate dot). The **reader** (the `<article>`) is the drill-down — one article, prev/next: a focused reading surface with just back / save / prev / next / a filter-picker opener. Touch prev/next is a **tracked two-page carousel**, not a blind swipe: the article translates 1:1 with the finger while a full preview PAGE of the neighbour — its real masthead and its real content, in the reader's own classes, with `<audio>`/`<video>` swapped for inert same-box stubs — slides in from the edge, so a partial drag PEEKS the actual next article, and release past a fifth of the surface (or a flick) commits through the same guarded step the keyboard uses while anything short of it snaps back (`gestures.ts` `setPager` + `pager.ts` + the shared fill in `article-view.ts`). It's **source-keyed** like the list — `app.ts` stamps `data-src` (`fmt.srcColorIndex`) on `.srr-reader`, coloring the mono **masthead** (`.srr-source` in the source color) over a **dateline** (`fmt.readerDateline`: an article from the last week leads with a compact **relative** age — "5h ago" / "just now" — the absolute date on hover, while older articles keep the absolute date with the relative age on hover). The whole masthead row (`.srr-title-row`, source · date · title) is the single "open original" **permalink** — the standalone globe/↗ icon and the inner title `<a>` are gone (a titleless feed hides just its `<h1>` so the source · date kicker stands in as the visible link). Its **prose is sans** (`--font-sans`, the reading voice it shares with headings) while the masthead/metadata/code stay mono (`--font-mono`, the "wire" voice — the "wire chrome wraps human prose" pairing); there is **no serif token and no webfont**, system stacks only, deliberately (`tokens.css`). In-content links/blockquote stay neutral ink. Its **content images open in a lightbox** (`lightbox.ts`) — a tap/click on a bare `.srr-content img` raises a dimmed full-viewport viewer with a tap-to-zoom stage, pinch-to-zoom + drag-to-pan touch gestures, and a ✕, Escape or a backdrop press closing it and focus returning to the image; an image the author wrapped in a link keeps its link instead. It is a modal like the settings/backup dialogs, so while it is up it owns the keyboard (capture-phase trap) and the swipe/cycle gestures see `lightbox.isOpen()` the way they see `picker.isOpen()`. **Edge feedback** spans list and reader: the list caps **both** ends with matched sign-offs over a dashed rule — "OLDEST" at the bottom (`.srr-wire-end`, `list.ts` `syncBottomTerminus`) and "LATEST" at the top (`.srr-wire-top`, `syncTopTerminus`), and in the reader an ARROW toward a dead edge rings a **margin bell** (`app.ts` `bumpReaderEdge` — a lateral rubber-band on `.srr-reader` + a pulse on the greyed ◀/▶ — `srr-bell-left/right` + `srr-edge-pulse`), the horizontal cousin of the list's keyboard row bump; the same wall met by a FINGER answers with resistance instead — the pager's damped dead-edge drag (`pager.ts`), felt during the gesture rather than announced after it. All of them honor `prefers-reduced-motion`. `app.ts` toggles them (`showList`/`showReader`; `srr-view-list` hides the reader-only prev/next + the save toggle + the back button). The toolbar (`.srr-toolbar`) holds the **list toolbar** (open-article · feed readout · filter) — the readout (`.srr-feed`) carrying the ellipsizing filter name (`.srr-feed-name`) and opening the anchored settings menu on tap — and the **reader toolbar** (back · ‹ prev · next › · save · filter) — the filter button (`.srr-filter`, an outline-funnel icon flush right in BOTH bars, the picker opener — see the filter picker below) — the prev/next pair centered in the thumb zone (`next` the emphasized accent pill, carrying the **pending readout** `.srr-next-count`: mono tabular digits showing what is live **unread and ahead** (`IShowFeed.right_count`, via `nav.pendingRight` — the picker badges' own tally with each member's frontier floored at the cursor, so it equals the picker on every recorded landing and ticks down by exactly 1 per forward step; an unrecorded landing reads one below the badge, which still counts the not-yet-consumed article on screen; saved/search count their explicit sets strictly after `pos`), formatted by `fmt.countBadge` ("999+" cap, shared with those badges), folded into the button's accessible name, shown whenever the count is known — the last article reads an explicit greyed "0 ›", and an honest "0" mid-history in show-read mode when only read articles remain ahead — and hidden only on an unknown (-1) probe; it **flares once** (`srr-next-pulse`, `prefers-reduced-motion`-exempt) when a background store refresh RAISES the count — `app.ts reprobeReaderChrome(pulseOnGrowth)`, passed `true` only by the post-refresh reconciliation and compared against the `lastNextCount` memo of what was last painted, so a user's own forward step never pulses), flanked by back/save at the edges — the back button carrying the **filter breadcrumb** `.srr-back-label`: a token in the filter picker rows' reading voice (sans at `--text-sm`, natural case — deliberately NOT the readout's mono/uppercase wire voice, so it matches the picker row that set it) naming the filtered lane prev/next walk and the list back returns to (`#tag` / feed title tinted with its `data-src` source color / ★ Saved), set by `refreshFeedLabel` alongside the list readout, folded into the button's aria-label/tooltip, and empty (hidden) on the unfiltered wire — silence means [ALL], the same neutrality rule as the list readout (search mode likewise stays unlabeled). The reader's pending readout doubles as the **frontier menu**'s one anchor: right-click / long-press (or the keyboard menu key) on the reader's next pill opens a small anchored card (`dropdown.showContextMenu`, wired by `app.ts` `bindFrontierMenu`) with the two seen-frontier gestures — "Mark all read" (the current selection's whole backlog) and "Mark unread from here" (the explicit rewind from the current article) — deliberately off the visible chrome; in the seen-neutral peek modes (saved/search) no items apply and the gesture falls through to the browser's own menu. The **filter picker** (`picker.ts`, `.srr-picker`) is a fixed full-viewport overlay over the list — not a view of its own (`view` stays `"list"`; `picker.isOpen()` gates the keymap/gestures instead) — opened by the toolbar's filter button (`.srr-filter`, flush right on both surfaces). It owns the filter rows — the `[ALL]` / "★ Saved" **scope-chip pair** side by side at the top (`.srr-picker-scope` / `.srr-scope-chip`: equal-width outlined pills — meta filters, not feeds, so no source chip; ★ Saved appears only when something is saved and `[ALL]` rides alone full-width until then), then tag groups and feeds with source-color chips, health-tinted labels, and async unread counts inline after each name (an italic, slightly smaller "×N" — the ★ Saved count reads the same way) — a header **Show read** toggle (`.srr-picker-showread`, `aria-pressed`, immediately left of the ✕ close; the unseen-only view mode, moved here from the settings menu — clicking it fires `onToggleShowRead` → app.ts's `toggleUnseenOnly`, which flips `nav.setUnreadOnly` and reconciles whichever surface the overlay is over (list `rerender` when visible, else `invalidate` the hidden list + re-probe the reader's chrome), then `picker.render()` re-derives its own rows for the new mode and the overlay stays open; `aria-pressed` = read shown = unseen-only OFF), a header **Info** stats toggle (`.srr-picker-info`, `aria-pressed`, left of Show read; while pressed a row tap opens that feed/tag/store detail card — the info dialog — instead of filtering; reset off on every `open()`), plus the feed/tag/store info dialogs those stats-mode taps open (the per-row ⓘ buttons are gone). It scrolls itself (`--z-overlay`, above the toolbar/search bar, below the modals), so the list's scroll position survives untouched underneath; ✕/Escape just close it, and picking a row closes it and routes per surface: from the list, `app.ts` routes `onSelect` through `selectFilter` (the same path as the two-finger/arrow cycle on the list — you land back on the headlines under the new lane, not in the reader); a pick from the **reader** (the same filter button over the article) stays IN the reader on the picked lane's resume article — the same semantics as the reader's W/S / two-finger filter cycle, and under split all three go through `app.laneChange`, which follows the switch with `landPaneOnLane`: a lane with no resume position would otherwise leave the always-on-screen pane BLANK beside a list that has just built it, while the identical pick with the list focused lands the pane on that lane's anchor, so it lands there too (`record: false`, `replace: true`). A pane that was ALREADY resting is still left resting, exactly as `selectTokens` leaves it — a pick is not a reason to start reading. The **settings menu** is the now-viewing readout's (`.srr-feed`, **list-only** — the reader toolbar has no readout; the readout's right-click/long-press stays the browser's own menu, deliberately not a frontier-menu anchor) anchored card (`dropdown.showContextMenu`, built fresh per open by `app.ts openSettingsMenu`): "Search articles…" (listed but disabled while `nav.searchAvailable()` is false), the **contextual offline-pin row** (only when pinning applies), and the keyboard-shortcuts / Stores / image-proxy / backup / sync dialog openers (the **Show read** toggle moved to the filter picker's header — above) — with the **freshness/degradation status footer** under the rows (`picker.renderStatus`: a relative-time-only "Updated X ago", amber flags for stale-fetch / index-rebuild / sync / refresh failures, the sync readout, and always the build's version label; `sync.init`'s status callback refills the footer of a menu that's open when a cycle lands). Unseen-only spans every filter ([ALL]/feed/tag), persisted in `srr-unread-only`. **Title search** is a pinned `.srr-search-input` bar (toggled via the settings menu's Search row / the `/` key, which works from the **reader** too — RDR8 — landing on the list in search mode, since search has always been a list filter mode): `input` is debounced (200ms) into `applySearchQuery` which sets the `q:<query>` filter, `replaceState`s `#!q:<query>`, and `list.rerender()`s. Search carries a **scope** (RDR8): entering it from a feed/tag lane keeps that lane (`#!q:<query>+<token>`, "search within this tag"), the bar's placeholder/`aria-label` name it, and leaving search returns to that lane rather than [ALL]; matched terms are `<mark>`ed in the result rows (`list.ts paintTitle`). The **backup/restore**, **sync** and **keyboard-shortcuts** dialogs live in `dropdown.ts` and the **feed/tag info dialog** in `picker.ts` (see below); the dialogs open from the settings menu, the info dialog from a stats-mode row tap in the picker. Hash scheme: a **numeric position** (`#pos[!tokens]`) is the reader; **no position** (`#` or `#!tokens`) is the list at that filter — where a `q:<query>` token (URL-encoded, e.g. `#!q%3Aclimate`), alone or beside one feed/tag token, is the **title-search filter mode** (see `nav.ts`). `app.route(hash)` picks the surface on boot and every `hashchange`; row-tap → `nav.goTo(chron)` (pushState reader hash) → reader; the back button (`goToList(true)`) / two-finger cycle → list; Escape closes an open picker first (staying on the list), else toggles reader ⇄ list. `srr-hash` persistence covers both surfaces, so a reload resumes where you were. Tapping a row commits into the reader; a filter change on the list re-filters and pushes a `#!filter` history entry without touching the reader's position, so browser-back walks back through those filters.

**Saved articles (`★`).** A per-article collection orthogonal to the feed/tag/seen axes: a device-local chronIdx set in `localStorage` `srr-saved` (`nav.toggleSaved`/`isSaved`/`savedCount`/`currentChron`). chronIdx is a permanent article address (finalized packs are immutable and never GC'd), so a saved id stays loadable forever — even after its feed is deleted (`feedTitle` then shows the `[DELETED]` tombstone). "★ Saved" is a **distinct nav mode** (`filter.saved`, reserved token `SAVED_TOKEN = "~saved"`): `filter.matches` becomes saved-set membership (feed-agnostic) and navigation walks the explicit set, not the idx packs. The set is stored in `srr-saved` in **save (insertion) order** — a save **appends** — so ★ Saved is a read-later queue consumed front-to-back: the view opens at the **front** (the earliest-*saved* article, NOT the lowest chronIdx) via `switchFilter` → `first` → `savedOrder()[0]` (`listAnchor` returns the same), read forward toward **newer saves**. Both nav and the list route their prev/next through one strict-neighbor seam — `nav.neighborOlder`/`neighborNewer` (saved → a save-index step, `savedNeighbor`, sound where the chronIdx ±1 trick would alias two numerically-adjacent saves; feed/search → the value seam `feedLeft`/`feedRight`); `step`/`first`/`last`/`goTo`/`showFeed` and `list`'s row walk all go through it, so save-order traversal is decided in one place. Un-saving the article currently on screen captures a **ghost anchor** (`savedGhost`, the save-index cousin of `filter.anchor`): `toggleSaved` snapshots the removed article's pre-removal queue neighbors and ahead-count, and `savedNeighbor`/`pendingRight` consult it while `pos` is no longer a set member — so prev/next, their enabled/disabled state, and the pending pill keep answering for the article on screen instead of dead-ending; the next landing (`resolve`/`resolveNoMatch`) clears it. The list suppresses day dividers here (like search — save order isn't date-monotonic). The reader has a `.srr-save` star toggle (key `b`, `aria-pressed`); list rows carry a tappable `.srr-row-star` (filled on a saved row) that toggles without opening the reader and, in the Saved view, drops the row on un-save — as does a rightward **swipe on the row** (RDR14; leftward toggles read, see `list.ts`). `getFilterEntries` lists `~saved` (when something is saved) but the W/S/↑↓/two-finger **rotation always skips it** (`cyclableLanes` drops `SAVED_TOKEN` in both modes) — ★ Saved is a deliberate pick from the filter picker, not a step in the unread sweep; the picker shows a "★ Saved" row (count badge) under `[ALL]`, picked via the same `selectFilter` path as a feed. Like the search filter mode, saved is a **peek mode**: `recordSeen` exempts it wholesale, so opening/browsing a saved article never touches any feed's seen frontier — re-reading an archived item isn't resuming its feed.

| Module | Role |
|---|---|
| `format.gen.ts` | **Generated — do not edit.** The TS side of the writer↔reader contract: format constants (`IDX_PACK_SIZE`, `META_PACK_SIZE`, `IDX_STATE_SIZE`, `IDX_HEADER_PREFIX`, `IDX_ENTRY_SIZE`, `IDX_BOUNDARY_SIZE`, `FEED_ID_CEILING`, `LATEST_KEEP`, `MAX_DELTAS`, `SEARCH_GRAM`, `SEARCH_BLOOM_BYTES`, `SEARCH_BLOOM_K`, …) and wire interfaces (`IArticleWire`/`IMetaWire`/`IFeedWire`/`IDBWire`) emitted from the backend Go declarations by `srr gen-ts`. `IFeedWire` is flat — `url`/`wm?`/`bg?`/`ferr?` live directly on it (`etag`/`last_modified` moved to the backend-only `seen.gz` sidecar and are no longer on the wire; the old `IFeedWire` is gone). Regenerate with `make generate`; `make verify` fails when stale. |
| `base.ts` | `PACK_BASE` — the URL every store key resolves against — and `VERSION`, the build's version label (the inlined `SRR_VERSION` define; exported from here because base.ts is the module the define transformer already covers). The neutral owner shared by `data.ts` (pack addressing) and `fmt.ts` (content-URL bounds check): neither module fits (fmt.ts is the sanitizer's home; importing data.ts triggers its eager db.gz fetch). |

## Data Structures

See root `CLAUDE.md` Data Contract for db.gz, IFeed, IArticle, pack format, CDN layout, and chronIdx.

Frontend-specific additions:
- `feeds` in `IDB` is `Record<number, IFeed>` (JSON object keyed by feed ID); defaults to `{}` if absent. `feed.id` is populated from object keys at init.
- **IArticle**: `{ f, a, p, t, l, c }` — feed_id, fetched_at, published, title, link, content. Loaded from JSONL data packs.
- **IShowFeed**: `{ has_left, has_right, right_count, article, placeholder?, notStarted?, startFeed? }` — `has_left`/`has_right` are computed by neighbor probes (`feedLeft(pos-1)`/`feedRight(pos+1)` with `.catch(()=>-1)`) so the prev/next buttons enable precisely when a step would move. `right_count` is the next pill's pending readout (`nav.pendingRight`): for feed/tag/[ALL], the filter's live unread with each member's frontier **floored at the cursor** — what is **unread AND ahead** (one shared tally body, `tallyWith`, behind both this and the picker badges, so they can only differ by the floor). On every recorded landing `recordSeen` has already raised the members to `pos`, so the floor is a no-op and the pill is exactly the picker badge — read-ahead articles are excluded (the earlier positional `countAll − countLeft(pos+1)` counted them and sat visibly above the `[ALL]` badge, the reported mismatch; the frontier pill before it froze at a phantom nonzero count while re-reading seen articles, the `#2810!english` bug — the floored count holds truthfully at 0 there instead). On an unrecorded landing (a switch resume, a restored `#pos` — landings that must not consume unread) the pill reads one below the badge: the badge counts the not-yet-consumed article on screen, the pill counts what → still has — which is what keeps the first step a −1 tick instead of a double drop when account-on-ENTER consumes the entry article and the landing together. The last article reads an explicit 0 on the disabled pill, recorded or not. Saved/search count their explicit sets strictly after `pos` (queue/hit countdowns — peek modes have no badge to agree with). `-1` = degraded count probe (digits hidden, next still works off `has_right`). `placeholder` is true only for the synthetic "(no matching articles)" article; `app.ts` renders it as the **shared directed empty state** (`list.emptyStateEl`, `.srr-list-empty` — same search/caught-up/saved/filtered wording as the list), hiding the article chrome via `.srr-reader-empty`, so the reader's no-match state and the list's speak one voice.
- Dev (`npm run dev` / `make dev-fe`): `concurrently` runs Parcel HMR (port 1234) + a CORS pack server (`serve`, port 3000). The pack server serves the **configured local store**, not a fixed path: `parcel/resolve-store.js` resolves the directory from `$SRR_STORE` → `store:` in the active config → `../packs` fallback (same precedence as the backend; an `s3://`/`sftp://` store, missing config, or absent dir falls back with a stderr note). Select a store with `SRR_CONFIG=~/.config/srr/srr.tmp.yaml make dev-fe`. The `serve` script forces `SRR_CDN_URL=http://localhost:3000` (the config's `cdn-url:` is a production same-origin path the local app can't use) unless `SRR_CDN_URL` is already set. `serve`'s directory listing lets you browse the pack files at `http://localhost:3000`. `frontend/.proxyrc.js` (dev-only connect middleware Parcel loads for `parcel serve`) rewrites a bare-root `GET /` to `/index.html` in place (no redirect — URL stays `http://localhost:1234/`); Parcel's dev server otherwise has no default-document and returns 403 on `/`. `parcel build` ignores it, so production is unaffected.

## Key Behaviors

**guard() mutex** (app.ts): all async UI actions go through it. Drops concurrent calls **while the hold is live**; a hold older than `BUSY_STUCK_MS` (60s) reads as stale and self-heals — the next swipe/arrow/button reclaims it instead of no-opping forever (`busyToken` ownership-guards `release()`/render so a stale owner that finally settles can't clear a newer holder's lock or paint its stale result over the live surface). On error → popup with retry (skipped if a newer holder has since reclaimed the mutex). Every store fetch (`data.ts`'s `fetchTimed`, covering db.gz plus every idx/data/meta pack) is itself abort-timed at `FETCH_TIMEOUT_MS` (30s) across both the request and the body read, so a stalled connection rejects — and `cachedPromise` drops the slot for a clean retry — instead of leaving the mutex wedged.

**Eager fetch**: `data.ts` starts `fetch("db.gz")` at module load (before `init()` call).

**Init**: `data.init()` loads db.gz, the idx header summary `idx/h<hdrs>.gz` (when `db.hdrs === numFinalizedIdx()`), and the latest idx pack — O(1) requests at any store size. Finalized idx packs are fetched lazily by chronIdx addressing when navigation touches them; `idxHeaders` (one `IdxHeader` per pack, latest last) powers sync counting (`countAll`), pack-skip deltas (`packHasCandidate`), and the pack-level timestamp search without any fetch. When `hdrs` lags or the summary fetch fails, init falls back to the old eager fetch-all path and peels each pack's own header (`hdrs` stays optional on the wire type — an absent value simply never equals `numFinalizedIdx()`). Tail packs are generation-named `L<tailGen>.gz` (`tailGen() = db.seq − nd`; `db.seq` normalized `??= 0` for the omitempty empty-store case) and the live delta chain rides `data/d<g>.gz`; every pack name is write-once, so all pack fetches use `cache: "force-cache"`. A non-OK response on a tail pack or delta segment means this tab's db.gz predates the backend GC grace window — `assertPackOk` triggers one `location.reload()` (sessionStorage-guarded against loops, guard cleared after a successful `init()`) and always throws so callers never touch the body. The reload is **scoped away from the background refresh**: a module-level `bgRefresh` flag is set around `refresh()`'s `applyDb` (cleared in a `finally`), and while it is set `assertPackOk` throws WITHOUT reloading — a transient tail 404 during the 5-minute heartbeat must not yank the app out from under a reading user, and `refresh()` already recovers by restoring the previous coherent snapshot wholesale and surfacing the failure through `lastRefreshError()`. Boot and user navigation keep the reload (the designed stale-tab self-heal); `refresh()` runs under `app.ts`'s `guardBg` mutex, so no user navigation can observe the flag set.

**Live content sync** (`refresh.ts`): an already-open tab silently adopts a newer store snapshot with no reload. `data.refresh()` re-fetches db.gz and, when `fetched_at`/`total_art`/`seq`/`gen` moved, re-runs the same boot body `init()` uses (`applyDb`) — every derived cache is recreated wholesale rather than diffed (a `gen` change, an in-place rebuild, takes the identical path since everything derived would be discarded anyway; the SW's own `checkManifest` purge rides this same db.gz response). On an `"updated"` result the trigger chains `search.invalidate()` → `nav.onStoreRefreshed()` (filter-stable adoption: bounds only ever rise, new/gone members join/leave, cached neighbor probes and any in-flight prefetch drop) → `app.ts`'s silent UI reconciliation (`refreshAfterStore`: toolbar label, the reader's chrome re-probed via `nav.probeCurrent()`, `list.onStoreGrown()`, an open picker repaint) — no content re-render, no scroll: the contract the whole feature is built to honor. Triggers: tab re-focus (60s throttle), regained connectivity, and a 5-minute heartbeat while visible — all background — plus the list's **pull to refresh** (the one manual trigger; a page reload is still the heavier one, re-fetching everything including the profile). The whole cycle runs under `app.ts`'s shared **`guardBg`** mutex (the background twin of `guard()` — same busy flag, no render/error popup, a losing caller is skipped rather than queued) so the swap can never interleave with a live navigation.

**Article loading**: `loadArticle(chronIdx)` resolves pack+offset via binary search on `IdxPack.bounds`, fetches and parses the JSONL data pack (LRU-cached by pack ID, max 20 packs).

**Neighbor prefetch** (nav.ts): after each `left()`/`right()`, the neighbor lookup (`findLeft`/`findRight` — may lazily fetch an idx pack) runs un-awaited off the critical path: its promise lands in `nextLeft`/`nextRight` (consumed by the next keypress; a rejection clears the slot instead of failing the committed navigation) and on resolution `schedulePrefetch(target)` warms the neighbor's media on `requestIdleCallback` (`{timeout:500}`; WebKit has no rIC, so a `setTimeout(…, 200)` fallback keeps iOS/Safari prefetching instead of stalling at every data-pack boundary) — it `loadArticle()`s the neighbor, runs `fmt.extractPrefetchMedia()` over its content (final render-path URLs: resolved, bounds-checked, proxied), and warms **capped** lists: the first `PREFETCH_IMAGES` (6) images/posters as `Image`s with `fetchPriority="low"`/`decoding="async"`, and the first `PREFETCH_VIDEOS` (2) video sources as detached `<video preload="metadata">` elements (duration/dimensions/first frame — cheap for faststart assets; preload is set before src, which triggers the media load algorithm). The caps are the point: uncapped, an image-stuffed neighbor (live store has 300+-image articles) split bandwidth so thin nothing completed before the next step and competed with the on-screen article's own lazy loads. `abortPrefetch()` cancels in-flight loads by setting `src=""` (WHATWG image-update steps for `<img>`, the media-load algorithm's abort for `<video>` — removing the attribute alone wouldn't abort) and dropping the refs — but **arriving at the prefetched article itself must not abort** (`resolve()` checks `currentPrefetch.target`): its in-flight loads are what the rendered content coalesces onto, so the refs are dropped without cancelling; any other navigation aborts. The `currentPrefetch` record (also the freshness token: a pending idle callback bails when `my !== currentPrefetch`) bounds memory to one neighbor at a time. Edits to nav must preserve this abort/freshness/arrival discipline.

**Content fade-in**: double `requestAnimationFrame` for opacity transition — skipped entirely on a **slide** entry (`reader.setEntryTransition`, a committed pager drag), whose drag already was the transition.

**Service worker** (`src/sw.ts`, registered best-effort from `app.ts` with `{type: "module"}` so it can import `LATEST_KEEP` from the generated contract — module-SW support predates the SW's `DecompressionStream` requirement in every engine, so the module type never limits compatibility): offline-capable cache. Lives at `src/` root (not `src/js/`) so Parcel emits it at the deployment root, giving it a default scope over the whole env (`/srr/`, `/srr.tmp/`, …). Buckets keyed by mutability: `srr-assets-v1` (content-hash `assets/…` — immutable, cache-first), `srr-packs-v3` (write-once pack names — finalized `idx|data|meta/<n>.gz`, latest generations `idx|data|meta/L<seq>.gz`, idx header summaries `idx/h<N>.gz`, and meta bloom summaries `meta/s<N>.gz` — cache-first with revalidate-on-miss; only `db.gz` is network-first → cache fallback; offline consistency is structural since a cached db.gz of seq N can only pair with the write-once `L<N>`), `srr-shell-v1` (navigation network-first + content-hashed JS/CSS cache-first; runtime-cached, no precache manifest — keeps the SW hand-written and zero-dep), `srr-meta-v1` (two synthetic entries: the last-seen db.gz `gen` and `seq`). **Manifest tracking** (`checkManifest`): on each successful online `db.gz` fetch whose `ETag`/`Last-Modified` differs from the cached copy's (an unchanged validator means unchanged bytes, so the common no-change load skips the parse and the redundant `cache.put` — a cheap header compare keeps the awaited check off the boot path's budget) the SW gunzips a clone (raw gzip bytes, no `Content-Encoding` — same manual `DecompressionStream` as `data.ts`) and reads `gen` + `seq` + `hdrs` + `mp` + `gcs` (absent == 0; `nd` is no longer needed — the L/d prune keys on `gcs`, the backend GC low-water, not on `tailGen`). One `parsePackName` helper (in `src/js/sw-grammar.ts`, extracted for unit-testability) owns the pack-name grammar (`series`/`kind`/`n`) for the fetch route, the cache bound, and the manifest prunes — built from the generated `PACK_SERIES_KINDS` table (backend `store.PackSeries`) and strict per-series like the store's `packKeyRe`: a kind letter another series owns (`data/h3.gz`) is not a pack name. A `gen` change (any change, not just increments) purges the whole packs bucket (in-place store rebuild — same names, new bytes); a `seq` change (gen unchanged) prunes cached tail generations `L<g>` AND delta segments `d<g>` with `g <= gcs` (db.gz's backend-GC low-water — the SW mirrors the store's own GC, evicting exactly what it deleted and keeping what it still serves; correct for offline reads at any runtime `--max-deltas` without the reader knowing that value, where a bare `tailGen - LATEST_KEEP` cutoff would evict the just-consolidated chain across a `tailGen` jump. `gcs` lags the live sweep one cycle — GC runs post-Commit — a safe direction), idx summaries `h<g>` with `g < hdrs - LATEST_KEEP`, and meta bloom summaries `meta/s<g>` with `g < mp - LATEST_KEEP` (all ride the `seq` prune signal rather than separate meta keys — each can advance without a seq bump on a zero-article retry cycle, but that strands at most one stale name until the next article-producing fetch). Both awaited *before* the db.gz response resolves, so the purge is race-free against the page's subsequent idx/data requests. Best-effort: a parse failure never blocks serving db.gz. The operator bumps `srr gen --bump` after an in-place store rebuild; the `srr-packs-vN` constant now only marks cache-format changes. **Cache bound** (`enforceCacheBounds`): after each successful online `db.gz` fetch (via `event.waitUntil`, off the critical path — and never offline, so a device can't lose a pack it can't refetch) each finalized pack series is capped per `SERIES_KEEP` — `idx`/`data` at `PACK_KEEP` (100), `meta` at `META_KEEP` (80, tighter because shards are ~200 KB gz each) — lowest-numbered evicted first (the numeric names encode chron age, so no access-time bookkeeping), and the assets bucket at `ASSET_KEEP` (500), oldest-cached first (Cache key insertion order; `cacheFirst` never re-puts on a hit). `db.gz` and the `L<seq>`/`h<N>`/`s<N>` names are exempt — offline consistency depends on them and checkManifest owns their pruning. Evicting a pack still being read just costs one CDN refetch on the next miss. Needs a secure context (HTTPS or localhost): production CF HTTPS qualifies, an `http://` LAN-IP deploy does not — registration just no-ops there and the app runs off the network. Coverage: `e2e/browser/reader.e2e.test.ts` ("serves the reader offline after one online visit", "purges stale finalized packs when db.gz gen changes", "bounds the pack and asset caches, evicting oldest entries first"). **Offline pin** (`srr-pinned-v1`): a fifth bucket, eviction-exempt and gen-purged, populated via the `"pin"` SW message from the page. The `⋯` overflow menu shows "Download for offline" / "Remove offline copy" for the current filter scope ([ALL] / feed / tag / unread — saved and search scopes are deferred to v2). On pin: `app.ts` calls `data.packNamesForFilter(filter.feeds)` to enumerate the exact write-once pack names (relative paths like `meta/0.gz`, `data/1.gz`, `idx/L1.gz` — the same form the fetch handler sees after the `/packs/` prefix), stores them in the `srr-pins` localStorage registry (`pin.ts`), and posts `{ type: "pin", names }` to the SW controller via a `MessageChannel`. The SW validates every name through `parsePackName` (no arbitrary cache-key injection), fetches each with `cache: "no-cache"` (ensures fresh bytes at pin time), and puts them into `srr-pinned-v1`. Progress is reported back as `{ type: "pin-progress", done, total }` messages and shown transiently in the status bar. The pack- and asset-fetch branches share one PINNED-first helper (`pinnedCacheFirst(req, bucket, revalidate)` — packs pass revalidate, content-hashed assets don't) that checks `srr-pinned-v1` before the rolling bucket, so a pinned pack serves offline even after the rolling-window PACKS eviction drops it. `enforceCacheBounds` never touches `srr-pinned-v1`. `checkManifest` purges `srr-pinned-v1` alongside `srr-packs-v3` on a gen change (in-place rebuild invalidates all cached pack bytes) but leaves it untouched on seq-only changes (latest packs are write-once generation-named — a cached `L<g>` in PINNED stays valid for its seq). On unpin: `app.ts` calls `unpinFilter(key)` (clears the registry entry) and posts `{ type: "unpin", names }` so the SW deletes the exact cache entries. **★-Saved asset pinning (FMT2a)**: a saved article keeps its TEXT forever (immutable packs) but loses its self-hosted images/media once the feed's `exp` window passes — and the backend cannot help, because the saved set is device-local. So `nav.setSavedHook` fires on every save/un-save (both paths — the reader star and the list row), and `app.ts`'s `syncSavedAssets` pins that article's `assets/…` keys (`fmt.extractAssetKeys`) into the SAME `srr-pinned-v1` bucket under its own registry scope `~saved:<chron>`, releasing them on un-save. The release runs through the shared `dropPinScope(key)`, which subtracts every name another pinned scope still references — so un-saving one article never deletes an image a different saved article (or a pinned filter) still shows. The pin path re-checks `nav.isSaved(chron)` **after** its `loadArticle` await, and that guard is load-bearing: the un-save path is synchronous, so a star tapped twice over a cold data pack runs it to completion *inside* that await, before there is any registry entry to release — pinning anyway would strand an un-saved article's media in the eviction-exempt PINNED bucket under a registry entry nothing ever clears, which would additionally make those names read as "still needed" when some other scope is released. **Storage persistence (PWA2)**: the first pin of either kind calls `navigator.storage.persist()` (once per page life, fire-and-forget). The PINNED bucket is exempt from SRR's OWN eviction, which is all the eviction SRR controls — under pressure the browser can still drop the whole origin — so this is what turns the offline-pin feature from best-effort into durable; asking on boot would prompt for something the user hasn't asked for yet. The unread-scope note: a pin is a snapshot — new unread arriving after the pin is not auto-pinned. Neutral pin/unpin copy. SW message protocol summary: `{ type: "pin", names: string[] }` (+ optional `MessagePort` in `ports[0]` for progress); `{ type: "unpin", names: string[] }` (remove specific entries); `{ type: "unpin-all" }` (clear all of PINNED). Coverage: `e2e/browser/reader.e2e.test.ts` ("caches named packs into srr-pinned-v1 on a 'pin' message", "pinned packs survive enforceCacheBounds (eviction-exempt)", "gen change purges srr-pinned-v1 alongside srr-packs-v3" — all three require SW controller, same sandbox limit as the pre-existing SW-controller tests). **Periodic warm (PWA5)** (`periodicsync` → `warmHome`): everything above needs a page to be running, and an installed PWA is launched cold — often offline, hours later. `periodicsync` is the one hook a CLOSED app gets, so the worker registers the tag `srr-db-warm` **itself** (`ensurePeriodicSync`, from `activate` and from every `"mounts"` post — a page boot is the cheapest recurring "the app may be installed now" signal, since the permission is granted at install time, long after the worker that first activated; once per worker lifetime, and an absent API / denied permission / rejected registration is a silent no-op, which is the whole Chromium-only progressive-enhancement story). `minInterval` is **12 h**, a FLOOR and not a schedule: the browser fires these at its own discretion, and the warm is not chasing the store's 5-minute commit loop but the next LAUNCH — a radio wake with no user present should be as rare as the window it covers, and a visible tab already has `refresh.ts`'s focus/online/5-minute triggers. What the handler must NOT do is "just fetch db.gz": caching a newer root alone would leave the next offline launch booting a generation whose idx tail it never fetched, breaking the structural pairing the whole offline story rests on. So `warmRoot` runs the STORE's own commit discipline on the client — publish the objects, flip the root last: fetch db.gz → `readAdoptable` (the read half of `checkManifest`, split out for exactly this, and which now THROWS rather than returns null when the manifest is unreachable, since "nothing to do" and "could not find out" are opposites here) → cache-first every name in `names.ts`'s `bootWarmNames` (every series' tail + the delta chain + `hsum`; deliberately not `ssum`, which serves search at 4 KB per finalized shard) → `adoptManifest` (the write half: evict + record) → cache db.gz → `enforceCacheBounds`. Any failure before those last two leaves the cached root exactly where it was, so a wake is never worse than not having tried; an OFFLINE wake throws at the first fetch before anything is written, which is what keeps the eviction and the cache bound on their documented "successful ONLINE db.gz fetch" trigger. Warming is **home-only**: the mount table carries roles, not which store is active, a cold launch resolves to home, and warming N peers would multiply an unattended wake's cost for stores the user reaches only by an explicit foreground act. Coverage: `src/js/names.test.ts` (`bootWarmNames` membership) and `e2e/browser/reader.e2e.test.ts` ("warms the new generation's boot objects on a periodicsync wake" — publishes a generation while the page idles, delivers the event through CDP's `ServiceWorker.dispatchPeriodicSyncEvent`, and asserts the cached root moved AND that generation's tails are cached with no page having asked for them; headless cannot be an installed app, so the worker's own `register()` is a no-op there and that half is not what the test proves).

**Reader render behaviours keyed to the article** (`reader.ts` `render`, around the `el.content.replaceChildren` block): the outgoing article's `<audio>`/`<video>` positions are HARVESTED before the replace and restored when you come back to it (FEB2 — `#enclosure` injects podcast `<audio controls>`, so one swipe used to kill a playing episode dead; POSITION only, never auto-resumed playback, and a `pendingRestore` WeakMap keeps a second render of the same article before its metadata lands from harvesting the still-zero value over the real one). `mediaStates` is keyed `` `<mid>:<chron>` `` — chronIdx is only unique WITHIN a mount (S38), so a bare-chron key restored one store's position onto another store's article. The five media steps around the replace run in a FIXED order — **harvest → adopt → replace → restore → rehome** — because harvest and rehome both pair state to elements BY INDEX over `querySelectorAll("audio,video")`, so adopting (which REMOVES one) before harvesting would shift every later index and misalign the whole article's saved positions. Step 3 (`replace`) now installs `buildContent(o.article, data.activeStore().base, { inert: false })` from `article-view.ts`, and `stampContentHost` applies the `lang`/`dir` stamp described next — the same two calls the pager's preview page makes, which is the whole point of them being one function each. The `harvest → adopt → replace → restore → rehome → chips` ORDER is untouched by that change and must stay so: the extraction deliberately slotted into the sequence rather than restructuring it. The content host is stamped with the article's own `lang` (the wire's `g`, from the backend's always-on detection) plus `dir="auto"` (RDR4 — otherwise everything inherits `<html lang="en">`: wrong screen-reader voice, English hyphenation patterns, undeclared-RTL rendered LTR); `.srr-content` sets `hyphens: auto`, which is only correct BECAUSE of that stamp, and an article the detector wasn't confident about carries no lang and simply isn't hyphenated.

**The mini-player** (RDR16, `player.ts` + `.srr-player`): FEB2 made stepping away non-destructive to media POSITIONS; this makes it non-destructive to PLAYBACK. The mechanism is **relocation, not reconstruction** — the live `<audio>`/`<video>` is MOVED out of `.srr-content` with one `appendChild` (an atomic remove+insert, which the HTML spec's "removed from a `Document`" steps let through because the pause check only fires when the element is *not* in a document at stable state) before `replaceChildren` would destroy it, and swapped back into its slot via `replaceWith` when you return to the owning article. Same node, same buffer: no second element, no `currentTime` handoff, no re-buffer gap — and video rides the identical path, CSS-constrained to a compact 16:9 frame (collapsed to audio's zero-width box on ≤500px phones, where the title needs the space more than a 64px cover-crop). Two concerns stay separate on purpose: **relocation is about survival** (the element moves only when its article stops being rendered), while **the bar is about control** (it shows whenever media is active and you cannot see it — its article isn't rendered, the reader is hidden behind the list, or the element is scrolled out of view via an `IntersectionObserver`), which is what makes the transport follow you down the show notes instead of the element leaping out of the prose. `controls` is dropped while in the bar and restored on rehome (`fmt.ts` force-sets it in content). Closing hands the position back to FEB2, so the article stays exactly as resumable as if the player had never been opened. **Media Session** publishes title/feed/album and play/pause/stop/seek handlers; `previoustrack`/`nexttrack` are registered ONLY while the playlist queue (below) is non-empty and step QUEUE items — they must never map to prev/next *article*, which would turn the lock screen into a way to skip out of the episode you are listening to (with no queue they stay unset, today's greyed-out behavior; previous follows the podcast convention — >3s in restarts, else the one-deep `lastPlayed` history, re-queuing the current episode at the front so ⏮ then ⏭ round-trips). **The playlist** (the "up next" queue, same module): `injectQueueChips()` — reader.ts's step 6, after rehome — puts a `+ Playlist`/`✓ Playlist` toggle chip (`.srr-queue-chip`, a `<button>`, so the FEB2/rehome `audio,video` index pairing is untouched) after every eligible in-content media element (not the GIF idiom, and only elements with a `src` attribute — a `<source>`-only element can't be rebuilt detached, the same bar `save()` sets). Entries carry the `Persisted` shape plus mid (`{mid, chron, index, src, kind, title, feedId}`), so playing one needs ZERO pack fetches; the active episode is never a member — playing an entry consumes it, manual in-content claims included. Auto-advance on `ended` (and skip-ahead on `error` — each attempt consumes an entry, so a run of dead episodes terminates at the quiet dismissal): an entry whose article is mounted is claimed in place, anything else is built detached in the bar host (the boot-restore path). With nothing active and a non-empty queue the bar shows a **READY state** — head-of-queue labels behind a play button, visible immediately, never autoplaying (the visible result of the first chip tap; deliberately NOT a paused in-place claim, whose bar would stay hidden by the you-can-see-it rule and whose consume-on-claim would flip the chip straight back to "+"). Bar chrome: `»` plays the next entry and `≡ N` opens the queue panel — both driven by the `hidden` attribute, which needs styles.css's per-button `[hidden]` restatement to actually blank them (the author `display: inline-flex` on the transport keys beats the UA sheet, the same cascade trap `.srr-player[hidden]` documents); on a ≤500px phone `»` is traded away entirely (the panel's row play buttons, auto-advance and Media Session all cover "next") and the transport track widens via `:has()` on the ≡ chip, because seven keys can never hold the ONE ROW every fixed-bottom lane's ~4rem arithmetic assumes; the same phone block also DECLUTTERS to ONE line (nothing in the controls column wraps — user call 2026-07-28): the clock hides, the keys ride flex-nowrap so no font or count can mint a second row, and a video's miniature collapses by WIDTH into the zero-width box audio rides (never display:none — the element must stay rendered for playback to survive); the seek rail deliberately stays desktop's tappable rail under the title — the phone's one progress display (a 2px read-only top-edge hairline was built and rejected the same day); the design-harness demo clock is scoped `min-width: 501px` because its higher-specificity fake would otherwise force a state no real phone bar reaches into every design shot (`.srr-player-panel`, lazily built child of `.srr-player` so it inherits the scrub-gesture guard; row tap = play now, row ▲/▼ = reorder — `moveQueued`, dead ends disabled not hidden, focus following the moved row across the re-render, the READY head re-labeling through `afterQueueChange` — row ✕ = remove, Escape/outside-press close, and its keydown stops propagation wholesale — the lightbox rule scoped to a popover). The rows also take a **swipe-to-remove** (`attachRowSwipe`): LOCAL touch handlers on purpose, because gestures.ts declines every touch starting inside `.srr-player` (the scrubber guard) so the document machine can never reach these rows — same `AXIS_SLOP`-shaped lock (vertical-dominant past the slop is a scroll for the gesture's life, an engaged drag preventDefaults so the panel can't scroll under it), the commit distance is gestures' own exported `ROW_SWIPE_TRIGGER`, a sub-trigger drag snaps back on the row's CSS transition, and a per-row `swallow` flag eats the finger-lift's synthesized click (list.ts's swipeClickGuard, scoped to the row). ✕ on the bar clears episode AND queue — an explicit "I am done". An erroring episode gets **one retry** before the quiet dismissal / queue skip: the first `error` keeps the claim, waits `RETRY_DELAY_MS` (2 s — an immediate reload lands inside the same blip), then `load()`s the SAME element, reseeks at metadata, clears `.srr-broken` (collapseBrokenMedia hid an in-content video on that same error) and resumes only if it was playing; `active.retried` makes the second error final, and `release()` cancels a pending retry. Mutation-checked against both reconstruction mutants (rebuild in `adoptFromContent`, rebuild in `rehomeInto`; both caught by node identity) and against a non-atomic move (`remove()` + a `setTimeout` re-insert, caught by `paused`). ⚠ One thing no test can catch, learned there: `remove()` immediately followed by `appendChild` **in the same task** is behaviourally identical to the single call — the spec's pause check runs at stable state, and Blink's is a zero-delay timer — so what must be protected is that the re-insert never crosses a task boundary, not the literal one-call form.

**Unread readout beyond the app's chrome** (RDR12): `syncUnreadBadge()` keeps `navigator.setAppBadge`/`clearAppBadge` (feature-detected on both sides) and a LEADING `(N)` in `document.title` in step with the ACTIVE store's [ALL] unread — the same tally the picker's `[ALL]` row shows, so the two can never disagree. The count leads rather than trails because a tab title truncates from the right. `setTitle(base)` is the single writer of `document.title` so the count and the surface's name can't drift; the badge re-syncs after a landing, a frontier gesture, a store refresh and a profile merge. The cached total seeds at **-1**, not 0, so the first sync always writes through: an app badge outlives the session that set it (it sits on the installed icon until something clears it), which makes a launch finding everything already read exactly the case that must call `clearAppBadge` — and a 0 seed would make it the one case skipped as "no change". Concurrent calls collapse to "one running, one more after" rather than dropping the later one, so a burst of navigation can't leave the badge on whichever count the in-flight run happened to read.

**Installable (PWA)** — `src/manifest.webmanifest` (linked from `index.html`) + the SW's fetch handler satisfy the browser install criteria. `shortcuts` offers Unread (`"./#!"`, the list at [ALL] — its oldest-unread anchor) and Saved articles (`"./#!~saved"`). ⚠ **Both halves of that string are load-bearing** and neither may be "simplified" away. The `./`: a shortcut `url` resolves against the **manifest's** URL, not the app's, so a bare `"#!~saved"` resolves to `/manifest.webmanifest#!~saved` — still inside `scope`, so nothing errors, it just silently opens the raw manifest JSON instead of the reader (the bug the first cut of this shipped). The `!`: the fragment must carry **at least one character** or it collapses in the URL parse — `new URL("./#", href).hash` is `""`, not `"#"` — so the Unread shortcut written `"./#"` boots with `location.hash` empty, app.ts's init falls through to the `srr-hash` localStorage restore, and the launcher lands wherever the user last was instead of the unread list it advertises (the second cut's bug, fixed 2026-07-26). `"./#!"` is the minimum non-collapsing list hash: `hash` is `"#!"`, so the restore is skipped; `hashPos("!")` is `""` so `route()` takes the list branch, `parseHashTokens("!")` is `[]` so the filter clears to [ALL], and route's own `replaceState` canonicalizes the URL back to `"#"` — the trailing `!` never survives into history. `start_url`/`scope` are `"."` for the same deployment-relative reason as the `./`, so the same bundle installs under `/srr/` or `/srr.tmp/`. JSON takes no comments, which is why the rule lives here. Icons: `src/icon.svg` is the single source of truth — the same RSS glyph as the inline favicon, recolored white on the brand-orange tile and inset into the maskable safe zone. The raster fallbacks are generated from it with `rsvg-convert -w N -h N src/icon.svg -o src/icon-N.png` (192, 512, and a 180 `apple-touch-icon.png`); the manifest also references `icon.svg` directly as a scalable `any` icon. Regenerate the PNGs whenever `icon.svg` changes. Coverage: `e2e/browser/reader.e2e.test.ts` ("exposes a valid, installable web app manifest").

## State Machines (nav.ts)

State: `pos` (chronIdx), `filter` (object with `active`, `feeds`, `tokens`, `matches()`, `clear()`, `set(tokens)`).

**`filter`** — active when `tokens` non-empty:
- `filter.clear()`: empties tokens, repopulates `feeds` from all feeds with `total_art > 0`
- `filter.set(tokens)`: resolves tokens (numeric feed IDs or tag names) into `feeds` map (`feed_id → add_idx`); falls back to `clear()` if no token resolves. Three modes short-circuit the feed resolution: `[SAVED_TOKEN]`, a lone `q:<query>` (both feed-agnostic, `feeds` stays empty), and (RDR8) `q:<query>` **plus one** feed/tag token — the scoped query, which fills `feeds` from the scope half (`filter.scope`, at natural `add_idx` bounds, no `applyUnseen`) and leaves the hit set to be intersected inside the scan
- `last(replace = false)`: jumps to the last matching article under the current filter (set the filter first via `filter.set`/`switchFilter`)
- `goTo(idx)`: navigate to chronIdx; if filter active and target doesn't match, snap forward to next match; falls back to `last()` if none
- `switchFilter(token)`: sets filter to token (or clears if `""`); resumes at last seen position for that feed/tag if valid (in unseen-only mode too — `isValidSeen` validates against the true `add_idx`, not the raised bound, so you open at your current position, not the oldest unseen; the landing becomes `filter.anchor`, so ← can step back to it after → walks into the unseen), otherwise jumps to `first()` (show-read) or a placeholder (unread-only, below). **In unread-only mode the reader is a resume surface, so a feed/tag with no already-read article to resume onto resolves to a placeholder (`resolveNoMatch`) rather than opening an unread article — two flavors keyed by `IShowFeed.notStarted`: a fully-read lane (no unread left — `noUnreadLeft`: nothing matches the raised bounds) shows the "All caught up" empty state (`notStarted: false`); a never-opened lane (has unread but `getSeen` is undefined) shows the distinct "Not started" empty state (`notStarted: true`, `list.emptyStateEl({notStarted, startFeed})`) with Next **armed** (`has_right` + the full-backlog pill == the picker badge) — a →-step starts reading at the oldest unread right there, no detour through the list — and `IShowFeed.startFeed` (that oldest-unread article's own feed, probed warm right after `noUnreadLeft`) lets the station name WHICH feed is the never-read one as its opening wire-head line (masthead-first, like the article that replaces it) — the masthead-voice name between dashed hairlines, source-tinted (`.srr-empty-name[data-src]` in `.srr-empty-wirehead`) — a tag lane's label alone couldn't say which member feed is new (probe-blip fallback: the lane label); "All caught up" would be false there (the lane HAS unread). (The pill tracks the picker badge — the same tally floored at the cursor, and with no article on screen the placeholder's pill IS the badge — so the placeholder is purely the resume-surface call: a mere switch must not drop the reader onto unread it won't record.) The caught-up guard also covers `fromHash` (a reload onto a caught-up lane) and the `""` ([ALL]) fully-caught-up case; the not-started placeholder is feed/tag-only — the `""` [ALL] case keeps landing on the oldest unseen. Show-read mode opens the article as before — you browse read items there.** `""` ([ALL]) opens at the **oldest unseen** article across all feeds (the same `oldestUnread` scan `listAnchor` uses), falling back to `last()` only when fully caught up. **Every switch landing resolves with `record: false`** — a filter switch (a picker click, and the W/S / ↑↓ / two-finger cycle via `cycleFilter`) is a resume, not a read, so it never advances the seen frontier: merely visiting a lane can't decrement its unread count, and a never-seen feed/tag lands on its oldest article still unread (show-read mode; in unread-only mode it shows the not-started placeholder instead — above). Reading forward (Right) records normally from there
- `cycleToken(dir)` (async): the next **cyclable** filter-entry token by `dir` (+1/-1) — it walks `getFilterEntries()` from `cycleOriginKey()` skipping non-cyclable lanes (`cyclableLanes`: ★ Saved is **always** skipped; in unread-only mode a tag/feed lane is skipped when it has 0 unread — `[ALL]` always survives), wrapping, so W/S/↑↓/swipe land only on lanes worth reading. Async because unread is idx-derived (`unreadCounts`)
- `cycleFilter(dir)`: `switchFilter(await cycleToken(dir))`
- `getFilterEntries()`: returns `["", "tagName", ..., "feedId", ...]` built via `data.groupFeedsByTag()`
- `getCurrentFilterKey()`: returns `""`, the single token, or `""` for multi-token filters (URL-only edge case)
- `filterLabel(key)`: resolves a filter key to its human label (`""`→"All", `SAVED_TOKEN`→"★ Saved", a `q:<query>` token→"Search: <query>", numeric feed id→`data.feedTitle`, tag name→itself) — total over every key shape nav produces, so no surface can print a raw id OR a raw `q:` token. The single source for the toolbar feed label, the document title, and the list's all-caught-up line, so none of them ever shows a raw feed id
- Navigation uses `findLeft`/`findRight` — async (may lazily fetch an idx pack); finalized packs without a filter match are skipped via summary header deltas, no fetch. `filter.clear()`/`set()` stay synchronous via `data.countAll`
- Hash: `#pos[!tokens]` — `!` segment, `+`-separated tokens, each `encodeURIComponent`-wrapped to survive special chars in tag names.
