# CLAUDE.md

## Project

SRR Frontend — single-page RSS reader. Zero runtime deps. Parcel + TypeScript + plain CSS.

## Commands

`npm run dev|build|test|typecheck|lint|format|format-check|smoke` — dev server, production build (`../dist/srrf/`), vitest+jsdom, **`tsc -p tsconfig.check.json`** (the type gate — see below), ESLint, Prettier write/check, boot smoke-test (`e2e/boot-smoke.mjs`). E2e entry points: `npm run test-contract|test-browser|test-stress` (each with its own `vitest.*.config.ts`; `vitest.shared.ts` holds common config), design harness `gen-design|shoot-design`, and `serve`/`servep` (the dev CORS pack server). Prefer the root `make` wrappers.

**The type gate** (`npm run typecheck` → `make typecheck-fe`, inside `make verify-fe`). Nothing else in the pipeline reads types: Parcel strips them without checking, vitest transpiles per file, and ESLint runs the non-type-aware ruleset — so until this existed a type could rot for releases with every gate green. It had: `IDB` was left extending the root POINTER after the manifest cutover moved every field the reader reads onto the manifest, and the entire data layer was checking against a shape nobody builds. It needs its own config (`tsconfig.check.json`) because the base `tsconfig.json` has no `include`, so a bare `tsc -p .` pulls in the e2e suites, the `.test.ts` files and `node_modules`' ambient types and buries the app's own errors in hundreds of irrelevant ones — which is why nobody ran it. The scoped config is `src/js/**` + `src/sw.ts`, tests excluded, `types: []`, ESM module mode (the base config's NodeNext would reject `app.ts`'s legitimate `import.meta`). **The tests are deliberately NOT in it** — the partial `vi.mock` factories are structurally incomplete by design.

## Architecture

> **Deep-dives live in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).** The module table below summarises every module; the ten largest rows (`data`, `nav`, `list`, `gestures`, `pager`, `picker`, `fmt`, `profile`, `sync`, `app`) were moved there verbatim and are linked from their row, as is `pane` — whose section also holds the split-view **chrome** (the toolbar rail, the resize grip, the hide controls), the one entry that is a surface rather than a module. Those summaries are lossy — read the companion section before editing one of those modules.

Entry: `src/index.html` → `src/styles.css` + `src/js/app.ts`. Bundler: Parcel 2. `SRR_CDN_URL` is replaced at build time: `parcel/resolve-cdn-url.js` resolves the value, `parcel/transformer-define.js` does the literal substitution in `base.ts` (it also inlines `SRR_VERSION` — `$VERSION` env, set to the tag by release.yml's build jobs, else "dev" — and `process.env.NODE_ENV`), and `parcel/optimizer-preload-db.js` injects a `<link rel="preload" … db.gz as="fetch">` into the HTML head. Resolution: env var → `cdn-url:` from `$SRR_CONFIG_INLINE` (raw YAML) → `cdn-url:` from `$SRR_CONFIG` (file path, default `$XDG_CONFIG_HOME/srr/srr.yaml`) → fallback `"."` (relative to `index.html`: with no cdn-url the store sits next to the bundle, so `PACK_BASE` resolves to the bundle's own directory — `base.ts`; the dev server doesn't hit this fallback, `serve` sets `SRR_CDN_URL=http://localhost:3000` explicitly). The resolver **normalizes a trailing slash**, because a store base is a DIRECTORY: the preload injector, the SW and `mounts.ts` each used to re-derive that while `base.ts`'s bare `new URL(SRR_CDN_URL, location)` did not, so a path-carrying `cdn-url: https://cdn/store` had the app fetching `https://cdn/db.gz` while the preload from this same resolver warmed `https://cdn/store/db.gz`. Byte-identical for every slash-safe value (`"."`, an origin, an already-slashed prefix). The config read (the INLINE → file → default chain) is shared with the dev pack server via `parcel/srr-config.js` (`readConfigYaml`/`parseKey`).

Dependency chain: `app → {reader, menus, search-ui, pin-ui} → els` (the four extracted UI controllers and the leaf DOM-reference map — **none of them imports `app`**; whatever they need from the orchestrator arrives through their `setup()` deps or as explicit arguments, which is what keeps the graph acyclic), `nav → {seen, saved, prefetch, route}` (the four extracted nav concerns — likewise none imports `nav`; shared state travels as explicit arguments), `app → schema → keys`, `app → nav → {data, search, fmt}`, `nav → data → {idx, cache, base}`, `app → fmt → base`, `app → list → {data, nav, fmt}` (plus `list → seen` for the row-swipe read toggle **only** — the one place outside `nav` that writes a frontier, because `nav.markAllRead`/`markUnreadFrom` bake in the ACTIVE FILTER's scope while a row gesture's scope is one feed and one chron; the `FrontierScope` argument is exactly the seam ENG3 created for a caller that knows its own scope, so this is a second CALLER, never a second write path — every tally, the seen map and the undo machinery still come through `nav`), `app → picker → {base, data, nav, fmt, search, seen}` (picker reaches `search` for its `fold` alone — the row-search matches on the SAME folded text the article index does, rather than a second normalizer — and `seen` for the read-only `readSeenFor` peer-store rollup alone), `app → dropdown → {fmt, profile}`, `app → lightbox → dropdown` (the content-image viewer, borrowing only the shared Tab trap — a pure UI module that touches no nav/data state), `app → pin`, `{app, list, pager, player} → gestures` (imports no app module — `list` reaches it only to REGISTER its two surface gestures, the pull-to-refresh action and the row swipe, `pager` only to register the reader's, never the other way, and `player` only for the `ROW_SWIPE_TRIGGER` and `AXIS_SLOP` constants, so the Up next list's own swipe locks and commits at the list rows' judgement), `app → pager → {article-view, data, els, fmt, gestures, nav}` (the reader swipe pager's DOM half; it imports neither `app` nor `reader`, so the committed step arrives as an injected callback), `{reader, pager} → article-view → {data, fmt, urlish, format.gen}` (the pure article fill BOTH article surfaces run — a leaf like `els.ts`/`urlish.ts`, taking its nodes as an `ArticleRefs` argument rather than importing `el`, which is exactly what lets a surface `index.html` never declared reuse it), `{app, nav, dropdown, picker} → sync → profile` (the cross-device sync engine over the portable profile), `{app, picker, list} → refresh → {data, nav, search}` (the live content-sync trigger module — see Key Behaviors), `{idx, data, sw, types.d} → format.gen` (generated, see below), `{data, sw} → names` (the manifest name table — and `gunzipStream`/`gunzipJson`, the ONE hand-rolled `DecompressionStream` in the reader: store objects are served as raw gzip with no `Content-Encoding`, and data.ts used to re-spell the `pipeThrough` for the binary idx buffer and the per-chunk data-pack decoder), `search → {data, cache, format.gen}` (and `list → search` for the RDR8 term highlighting alone — `matchSpans`, so the marks agree with the fold the hits were found on; search.ts stays DOM-free and hands back raw-string ranges), `sw → sw-grammar → format.gen`, `* → model → signals` (each module owns its atoms; `effects.ts` reads them), `app → {effects, layout}`, `{effects, search-ui} → layout → {model, signals}`, `split → {model, signals}`, `{app, nav, fmt, pin, profile, sync} → keys` (the localStorage-key constants hub), `{app, picker, fmt, profile, sync} → urlish` (the side-effect-free http(s)-URL rules hub — `URL_DENY` + validate/normalize). All in `src/js/` except `sw.ts`, which sits at `src/` (its own row below says so too), strict mode. (`nav` owns the search **filter mode**, so it imports `search`; `dropdown` no longer imports `nav` or `data` — those moved to `picker.ts`.)

**Two surfaces + two popups.** `app.ts` switches surfaces via `showList` / `showReader`, which write `model.focus`; the filter-picker overlay and the settings menu (below) are popups over the list, not views of their own. **Split view** (`split.ts`, ≥1000px) shows both surfaces at once instead of switching between them: the list becomes a fixed self-scrolling pane and the reader fills the rest of the page, scrolling the window. `focus` is which pane has **keyboard focus**, never which pane is visible: every visibility question reads the **layout record** (`layout.ts` `layout()` — `listMounted`/`readerMounted`/`readerLive`/`readerSteppable`/`listKeys` over `model.split`/`focus`/`paneHidden`/`readerPainted`/`cursor`), and ONE effect is the only writer of the layout's body classes and both hosts' `hidden`. `readerLive` needs `readerPainted` (set by `render`'s article branch, cleared by every placeholder path and by a store switch) AND a cursor, because `model.cursor` is the cursor the LIST moves too. Only the sites listed in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#the-layout-record) may read the record's `focus`. `showList`/`showReader` still run but neither hides the other pane; with nothing open the reader shows its **resting panel** (`effects.ts`'s `restingPane` effect → `nav.restingState` → `reader.renderResting`) — the same directed empty state the reader shows at a dead end, Next armed off `has_right` so "Tap Next to start reading" is true — rather than leaving two thirds of the window blank under dead arrows. Its armed Next routes through `app.enterReader` for **any** article-less pane under split (`isSplit() && !reader.hasArticle()`), not just the resting one: `nav.switchFilter`'s own "not started" placeholder paints the same panel from the same `pos = -1`, and a `nav.right()` step from either lands one PAST the cursor the list pane has already seeded — opening the lane's SECOND article and marking the first read behind you. A resting paint is deliberately NOT a navigation: no surface flip, no `document.title`, no focus grab, no hash write. What they deliberately DON'T do is drive the reader-only toolbar state — prev/next enablement belongs to the probe, and every hide rule is `:not(.srr-split)`-guarded, so the toolbar's prev/next/save stay on screen from the list pane — nor any highlight: `.srr-row-current` is re-derived by `list.refresh()` via `followCursor()`. Opening an article from the list brings the list along instead of replacing it: every reader-pane step (arrow keys, the pager, a picker pick) moves `model.cursor`, and the `listRows` effect calls `list.followCursor()` to re-derive the highlight and scroll the cursor row into the pane's live band. Opening the article the pane ALREADY holds is a focus change, not a render — one door (`app.openArticle`) shared by Escape and the row tap, since two affordances for one act answer it differently unless they share a body; it re-renders only when the mounted chron and the cursor both name something else, and it still `nav.publishHash()`es + `persistHash`es, because the URL is what a copied link shares and what a reload restores from (skipping it left Escape, Escape, reload landing on an empty resting pane). Two panes also mean two paints of ONE ★ set and ONE seen map on screen at once. Both are model atoms (`model.saved`, `model.seen`), so a row's star, a row swipe, the reader's save button, its pending pill and the tab badge re-derive from the same write through `effects.ts` — no surface tells another. Deep-linking straight to `#pos` builds the list pane beside it through that same seam, NOT through `route()`: its numeric-position branch deliberately makes no list call, because the `listRows` effect runs `followCursor()` once the landing's rendering hold ends, whose not-yet-built fallback is `show(true)`. The phone-only touch gestures — toolbar auto-hide, pull-to-refresh, and the pager drag — stand down under `body.srr-split` (three class checks in `gestures.ts`, not an import, since a permanent two-pane chrome has nothing to hide, no overscroll edge to pull from, and nothing to clip a reader slide off the list pane); the hash grammar is unchanged (`#pos!tokens` addresses both panes; a `#!tokens` hash leaves the reader pane RESTING only before the session's first article, and after the first open both panes stay live, so browser-back to a list hash keeps the article beside the list exactly as Escape does — another lane's hash lands the pane like a pick; `split.e2e.test.ts` pins that contract). Keyboard: with a live pane the reader keymap runs from BOTH surfaces (`readerSteppable`) — ←/→ step the article the toolbar's ‹ › beside them step, since under split the row cursor IS the reader's article; the list's own row stepping (`list.moveSelection`) is what stands down there, and the filter-cycle keys stay on the list path (`onCycle`). A store refresh and a sync merge reconcile both panes through the same table (`listGrowth`, `listRows`, `readerChrome`), which reads `layout()` rather than focus. The **list** (`list.ts`) is home: a scannable headline feed under the current filter, newest-first, **source-keyed** — each row carries a per-feed color rail + a colored mono "source · age" eyebrow over the title (`fmt.srcColorIndex` → `data-src`; read/unread shows as title weight/brightness + rail saturation, no separate dot). The **reader** (the `<article>`) is the drill-down — one article, prev/next: a focused reading surface with just back / save / prev / next / a filter-picker opener. Touch prev/next is a **tracked two-page carousel**, not a blind swipe: the article translates 1:1 with the finger while a full preview PAGE of the neighbour — its real masthead and its real content, in the reader's own classes, with `<audio>`/`<video>` swapped for inert same-box stubs — slides in from the edge, so a partial drag PEEKS the actual next article, and release past a fifth of the surface (or a flick) commits through the same guarded step the keyboard uses while anything short of it snaps back (`gestures.ts` `setPager` + `pager.ts` + the shared fill in `article-view.ts`). It's **source-keyed** like the list — `app.ts` stamps `data-src` (`fmt.srcColorIndex`) on `.srr-reader`, coloring the mono **masthead** (`.srr-source` in the source color) over a **dateline** (`fmt.readerDateline`: an article from the last week leads with a compact **relative** age — "5h ago" / "just now" — the absolute date on hover, while older articles keep the absolute date with the relative age on hover). The whole masthead row (`.srr-title-row`, source · date · title) is the single "open original" **permalink** — the standalone globe/↗ icon and the inner title `<a>` are gone (a titleless feed hides just its `<h1>` so the source · date kicker stands in as the visible link). Its **prose is sans** (`--font-sans`, the reading voice it shares with headings) while the masthead/metadata/code stay mono (`--font-mono`, the "wire" voice — the "wire chrome wraps human prose" pairing); there is **no serif token and no webfont**, system stacks only, deliberately (`tokens.css`). In-content links/blockquote stay neutral ink. Its **content images open in a lightbox** (`lightbox.ts`) — a tap/click on a bare `.srr-content img` raises a dimmed full-viewport viewer with a tap-to-zoom stage, pinch-to-zoom + drag-to-pan touch gestures, and a ⌄ at the top left, Escape or a backdrop press closing it and focus returning to the image; an image the author wrapped in a link keeps its link instead. It is a modal like the settings/backup dialogs, so while it is up it owns the keyboard (capture-phase trap) and the swipe/cycle gestures see `lightbox.isOpen()` the way they see `picker.isOpen()`. **Edge feedback** spans list and reader: the list caps **both** ends with matched sign-offs over a dashed rule — "OLDEST" at the bottom (`.srr-wire-end`, `list.ts` `syncBottomTerminus`) and "LATEST" at the top (`.srr-wire-top`, `syncTopTerminus`), and in the reader an ARROW toward a dead edge rings a **margin bell** (`reader.ts` `bumpReaderEdge` — a lateral rubber-band on `.srr-reader` + a pulse on the greyed ◀/▶ — `srr-bell-left/right` + `srr-edge-pulse`), the horizontal cousin of the list's keyboard row bump; the same wall met by a FINGER answers with resistance instead — the pager's damped dead-edge drag (`pager.ts`), felt during the gesture rather than announced after it. All of them honor `prefers-reduced-motion`. `layout.ts`'s effect stamps the surface classes from `model.focus` (`srr-view-list` hides the reader-only prev/next + the save toggle + the back button). The toolbar (`.srr-toolbar`) holds the **list toolbar** (open-article · feed readout · filter) — the readout (`.srr-feed`) carrying the ellipsizing filter name (`.srr-feed-name`) and opening the anchored settings menu on tap — and the **reader toolbar** (back · ‹ prev · next › · save · filter) — the filter button (`.srr-filter`, an outline-funnel icon flush right in BOTH bars, the picker opener — see the filter picker below) — the prev/next pair centered in the thumb zone (`next` the emphasized accent pill, carrying the **pending readout** `.srr-next-count`: mono tabular digits showing what is live **unread and ahead** (`IShowFeed.right_count`, via `nav.pendingRight` — the picker badges' own tally with each member's frontier floored at the cursor, so it equals the picker on every recorded landing and ticks down by exactly 1 per forward step; an unrecorded landing reads one below the badge, which still counts the not-yet-consumed article on screen; saved/search count their explicit sets strictly after `pos`), formatted by `fmt.countBadge` ("999+" cap, shared with those badges), folded into the button's accessible name, shown whenever the count is known — the last article reads an explicit greyed "0 ›", and an honest "0" mid-history in show-read mode when only read articles remain ahead — and hidden only on an unknown (-1) probe; it **flares once** (`srr-next-pulse`, `prefers-reduced-motion`-exempt) when a background store refresh RAISES the count — the `readerChrome` effect's `applyChrome`, pulsed only when `model.storeGrown` moved since the last paint, compared against the `lastNextCount` memo of what was last painted, so a user's own forward step never pulses), flanked by back/save at the edges — the back button carrying the **filter breadcrumb** `.srr-back-label`: a token in the filter picker rows' reading voice (sans at `--text-sm`, natural case — deliberately NOT the readout's mono/uppercase wire voice, so it matches the picker row that set it) naming the filtered lane prev/next walk and the list back returns to (`#tag` / feed title tinted with its `data-src` source color / ★ Saved), set by `feedLabel` alongside the list readout, folded into the button's aria-label/tooltip, and empty (hidden) on the unfiltered wire — silence means [ALL], the same neutrality rule as the list readout (search mode likewise stays unlabeled). The reader's pending readout doubles as the **frontier menu**'s one anchor: right-click / long-press (or the keyboard menu key) on the reader's next pill opens a small anchored card (`dropdown.showContextMenu`, wired by `menus.ts` `bindFrontierMenu`) with the two seen-frontier gestures — "Mark all read" (the current selection's whole backlog) and "Mark unread from here" (the explicit rewind from the current article) — deliberately off the visible chrome; in the seen-neutral peek modes (saved/search) no items apply and the gesture falls through to the browser's own menu. The **filter picker** (`picker.ts`, `.srr-picker`) is a fixed full-viewport overlay over the list — not a view of its own (focus stays on the list; `picker.isOpen()` gates the keymap/gestures instead) — opened by the toolbar's filter button (`.srr-filter`, flush right on both surfaces). It owns the filter rows — the `[ALL]` / "★ Saved" **scope-chip pair** side by side at the top (`.srr-picker-scope` / `.srr-scope-chip`: equal-width outlined pills — meta filters, not feeds, so no source chip; ★ Saved appears only when something is saved and `[ALL]` rides alone full-width until then), then tag groups and feeds with source-color chips, health-tinted labels, and async unread counts inline after each name (an italic, slightly smaller "×N" — the ★ Saved count reads the same way) — a header **Show read** toggle (`.srr-picker-showread`, `aria-pressed`, immediately left of the ✕ close; the unseen-only view mode, moved here from the settings menu — clicking it fires `onToggleShowRead` → app.ts's `toggleUnseenOnly`, which is just `nav.setUnreadOnly` + `rerunPlaceholder()` — the `model.unreadOnly` write alone; the `listSurface`/`readerChrome`/`pickerRows` effects reconcile whichever surfaces are mounted, `pickerRows` re-deriving the open picker's own rows for the new mode, and the overlay stays open; `aria-pressed` = read shown = unseen-only OFF), a header **Info** stats toggle (`.srr-picker-info`, `aria-pressed`, left of Show read; while pressed a row tap opens that feed/tag/store detail card — the info dialog — instead of filtering; reset off on every `open()`), plus the feed/tag/store info dialogs those stats-mode taps open (the per-row ⓘ buttons are gone). It scrolls itself (`--z-overlay`, above the toolbar/search bar, below the modals), so the list's scroll position survives untouched underneath; ⌄ (top left)/Escape just close it, and picking a row closes it and routes per surface: from the list, `app.ts` routes `onSelect` through `selectFilter` (the same path as the two-finger/arrow cycle on the list — you land back on the headlines under the new lane, not in the reader); a pick from the **reader** (the same filter button over the article) stays IN the reader on the picked lane's resume article — the same semantics as the reader's W/S / two-finger filter cycle, and under split all three go through `app.laneChange`, which follows the switch with `landPaneOnLane`: a lane with no resume position would otherwise leave the always-on-screen pane BLANK beside a list that has just built it, while the identical pick with the list focused lands the pane on that lane's anchor, so it lands there too (`record: false`, `replace: true`). A pane that was ALREADY resting is still left resting, exactly as `selectTokens` leaves it — a pick is not a reason to start reading. The **settings menu** is the now-viewing readout's (`.srr-feed`, **list-only** — the reader toolbar has no readout; the readout's right-click/long-press stays the browser's own menu, deliberately not a frontier-menu anchor) anchored card (`dropdown.showContextMenu`, built fresh per open by `menus.ts openSettingsMenu`): "Search articles…" (listed but disabled while `nav.searchAvailable()` is false), the **contextual offline-pin row** (only when pinning applies), and "Mark all as read" (the frontier menu's whole-backlog raise, on the list's lane — absent on peek or empty lanes), and the Reading / shortcuts-and-gestures / Stores / image-proxy / backup / sync dialog openers (the **Show read** toggle moved to the filter picker's header — above) — with the **freshness/degradation status footer** under the rows (`picker.renderStatus`: a relative-time-only "Updated X ago", amber flags for stale-fetch / index-rebuild / sync / refresh failures, the sync readout, and always the build's version label; the `pickerStatus` effect refills the footer of a menu that's open when a cycle lands). Unseen-only spans every filter ([ALL]/feed/tag), persisted in `srr-unread-only`. **Title search** is a pinned `.srr-search-input` bar (toggled via the settings menu's Search row / the `/` key, which works from the **reader** too — RDR8 — landing on the list in search mode, since search has always been a list filter mode): `input` is debounced (200ms) into `applySearchQuery` which sets the `q:<query>` filter (the `model.laneTokens` write) and `replaceState`s `#!q:<query>`; the `listSurface` effect picks up that write and rebuilds the list via `list.reconcile()`. Search carries a **scope** (RDR8): entering it from a feed/tag lane keeps that lane (`#!q:<query>+<token>`, "search within this tag"), the bar's placeholder/`aria-label` name it, and leaving search returns to that lane rather than [ALL]; matched terms are `<mark>`ed in the result rows (`list.ts paintTitle`). The **backup/restore**, **sync** and **keyboard-shortcuts** dialogs live in `dropdown.ts` and the **feed/tag info dialog** in `picker.ts` (see below); the dialogs open from the settings menu, the info dialog from a stats-mode row tap in the picker. Hash scheme: a **numeric position** (`#pos[!tokens]`) is the reader; **no position** (`#` or `#!tokens`) is the list at that filter — where a `q:<query>` token (URL-encoded, e.g. `#!q%3Aclimate`), alone or beside one feed/tag token, is the **title-search filter mode** (see `nav.ts`). `app.route(hash)` picks the surface on boot and every `hashchange`; row-tap → `nav.goTo(chron)` (pushState reader hash) → reader; the back button (`goToList(true)`) / two-finger cycle → list; Escape closes an open picker first (staying on the list), else toggles reader ⇄ list. `srr-hash` persistence covers both surfaces, so a reload resumes where you were. Tapping a row commits into the reader; a filter change on the list re-filters and pushes a `#!filter` history entry without touching the reader's position, so browser-back walks back through those filters.

**The split view's chrome.** Above the breakpoint the toolbar is a **full-width rail** cut into one grid segment per pane. `.srr-tb-pane` IS the pane — it reads the same `--split-pane-w` the pane's own width reads, so the two cannot disagree by a pixel — and carries the pane toggle, the now-viewing readout and the filter funnel over the surface they act on rather than 700px away over one they don't touch; `.srr-tb-reader` is everything left of the window, which is exactly the box `.srr-container` centres in, so centring the back/prev/next/save group in it as ONE unit lands the accent next pill on the reading column's midline at any window width and any pane width. Below the breakpoint both wrappers are `display: contents`, so every button is a direct grid item of the bar again and the phone templates place exactly what they always did. The seam between the two segments is the **resize grip** (`.srr-pane-grip`): a real ARIA window splitter (`role="separator"` + live `aria-value*`), transparent at rest and `--accent` under the cursor or while dragging, driven by pointer capture and by the keyboard (←/→ 16px, Shift 64px, Home/End to the floor/ceiling, double-click resets to 380, Enter/Space hides). **Three doors hide the pane deliberately** — the rail's toggle button, the grip's Enter, and the `L` key — plus two that are not aimed at hiding at all: a drag under 240px collapses instead of clamping, and the grip's ARROW keys walk the width down unclamped through the same threshold (from the 280 floor one Shift+← lands on 216). Those last two are why the toggle's label syncs from `applyHidden` rather than from the committed setter; note the arrow path also `display:none`s the grip, so the key that did it cannot undo it. A hidden pane keeps its real width and stays laid out, taken off screen by `visibility: hidden` + a transform, never `display: none` (which would destroy its `scrollTop`), so showing it again is a pure class removal. `enterSearch` **un-hides**: the pinned search bar rides the pane AT THE PANE'S WIDTH, so over a hidden pane it is a 0px box — a correctness rule, not a courtesy, and `enterSearch` is the one funnel both the `/` key and the settings-menu row go through. **Full detail: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#panets-and-the-split-view-chrome)**

**Saved articles (`★`).** A per-article collection orthogonal to the feed/tag/seen axes: a device-local chronIdx set in `localStorage` `srr-saved` (`nav.toggleSaved`/`isSaved`/`savedCount`/`currentChron`). chronIdx is a permanent article address (finalized packs are immutable and never GC'd), so a saved id stays loadable forever — even after its feed is deleted (`feedTitle` then shows the `[DELETED]` tombstone). "★ Saved" is a **distinct nav mode** (`filter.saved`, reserved token `SAVED_TOKEN = "~saved"`): `filter.matches` becomes saved-set membership (feed-agnostic) and navigation walks the explicit set, not the idx packs. The set is stored in `srr-saved` in **save (insertion) order** — a save **appends** — so ★ Saved is a read-later queue consumed front-to-back: the view opens at the **front** (the earliest-*saved* article, NOT the lowest chronIdx) via `switchFilter` → `first` → `savedOrder()[0]` (`listAnchor` returns the same), read forward toward **newer saves**. Both nav and the list route their prev/next through one strict-neighbor seam — `nav.neighborOlder`/`neighborNewer` (saved → a save-index step, `savedNeighbor`, sound where the chronIdx ±1 trick would alias two numerically-adjacent saves; feed/search → the value seam `feedLeft`/`feedRight`); `step`/`first`/`last`/`goTo`/`showFeed` and `list`'s row walk all go through it, so save-order traversal is decided in one place. Un-saving the article currently on screen captures a **ghost anchor** (`savedGhost`, the save-index cousin of `filter.anchor`): `toggleSaved` snapshots the removed article's pre-removal queue neighbors and ahead-count, and `savedNeighbor`/`pendingRight` consult it while `pos` is no longer a set member — so prev/next, their enabled/disabled state, and the pending pill keep answering for the article on screen instead of dead-ending; the next landing (`resolve`/`resolveNoMatch`) clears it. The list suppresses day dividers here (like search — save order isn't date-monotonic). The reader has a `.srr-save` star toggle (key `b`, `aria-pressed`); list rows carry a tappable `.srr-row-star` (filled on a saved row) that toggles without opening the reader and, in the Saved view, drops the row on un-save — as does a rightward **swipe on the row** (RDR14; leftward toggles read, see `list.ts`). `getFilterEntries` lists `~saved` (when something is saved) but the W/S/↑↓/two-finger **rotation always skips it** (`cyclableLanes` drops `SAVED_TOKEN` in both modes) — ★ Saved is a deliberate pick from the filter picker, not a step in the unread sweep; the picker shows a "★ Saved" row (count badge) under `[ALL]`, picked via the same `selectFilter` path as a feed. Like the search filter mode, saved is a **peek mode**: `recordSeen` exempts it wholesale, so opening/browsing a saved article never touches any feed's seen frontier — re-reading an archived item isn't resuming its feed.

## Data Structures

See root `CLAUDE.md` Data Contract for db.gz, IFeed, IArticle, pack format, CDN layout, and chronIdx.

Frontend-specific additions:
- `feeds` in `IDB` is `Record<number, IFeed>` (JSON object keyed by feed ID); defaults to `{}` if absent. `feed.id` is populated from object keys at init.
- **IArticle**: `{ f, a, p, t, l, c }` — feed_id, fetched_at, published, title, link, content. Loaded from JSONL data packs.
- **IShowFeed**: `{ has_left, has_right, right_count, article, placeholder?, notStarted?, startFeed? }` — `has_left`/`has_right` are computed by neighbor probes (`feedLeft(pos-1)`/`feedRight(pos+1)` with `.catch(()=>-1)`) so the prev/next buttons enable precisely when a step would move. `right_count` is the next pill's pending readout (`nav.pendingRight`): for feed/tag/[ALL], the filter's live unread with each member's frontier **floored at the cursor** — what is **unread AND ahead** (one shared tally body, `tallyWith`, behind both this and the picker badges, so they can only differ by the floor). On every recorded landing `recordSeen` has already raised the members to `pos`, so the floor is a no-op and the pill is exactly the picker badge — read-ahead articles are excluded (the earlier positional `countAll − countLeft(pos+1)` counted them and sat visibly above the `[ALL]` badge, the reported mismatch; the frontier pill before it froze at a phantom nonzero count while re-reading seen articles, the `#2810!english` bug — the floored count holds truthfully at 0 there instead). On an unrecorded landing (a switch resume, a restored `#pos` — landings that must not consume unread) the pill reads one below the badge: the badge counts the not-yet-consumed article on screen, the pill counts what → still has — which is what keeps the first step a −1 tick instead of a double drop when account-on-ENTER consumes the entry article and the landing together. The last article reads an explicit 0 on the disabled pill, recorded or not. Saved/search count their explicit sets strictly after `pos` (queue/hit countdowns — peek modes have no badge to agree with). `-1` = degraded count probe (digits hidden, next still works off `has_right`). `placeholder` is true only for the synthetic "(no matching articles)" article; `app.ts` renders it as the **shared directed empty state** (`list.emptyStateEl`, `.srr-list-empty` — same search/caught-up/saved/filtered wording as the list), hiding the article chrome via `.srr-reader-empty`, so the reader's no-match state and the list's speak one voice.
- Dev (`npm run dev` / `make dev-fe`): `concurrently` runs Parcel HMR (port 1234) + a CORS pack server (`serve`, port 3000). The pack server serves the **configured local store**, not a fixed path: `parcel/resolve-store.js` resolves the directory from `$SRR_STORE` → `store:` in the active config → `../packs` fallback (same precedence as the backend; an `s3://`/`sftp://` store, missing config, or absent dir falls back with a stderr note). Select a store with `SRR_CONFIG=~/.config/srr/srr.tmp.yaml make dev-fe`. The `serve` script forces `SRR_CDN_URL=http://localhost:3000` (the config's `cdn-url:` is a production same-origin path the local app can't use) unless `SRR_CDN_URL` is already set. `serve`'s directory listing lets you browse the pack files at `http://localhost:3000`. `frontend/.proxyrc.js` (dev-only connect middleware Parcel loads for `parcel serve`) rewrites a bare-root `GET /` to `/index.html` in place (no redirect — URL stays `http://localhost:1234/`); Parcel's dev server otherwise has no default-document and returns 403 on `/`. `parcel build` ignores it, so production is unaffected.

## Key Behaviors

**guard() mutex** (app.ts): all async UI actions go through it. Drops concurrent calls **while the hold is live**; a hold older than `BUSY_STUCK_MS` (60s) reads as stale and self-heals — the next swipe/arrow/button reclaims it instead of no-opping forever (`busyToken` ownership-guards `release()`/render so a stale owner that finally settles can't clear a newer holder's lock or paint its stale result over the live surface). On error → popup with retry (skipped if a newer holder has since reclaimed the mutex). Every store fetch (`data.ts`'s `fetchTimed`, covering db.gz plus every idx/data/meta pack) is itself abort-timed at `FETCH_TIMEOUT_MS` (30s) across both the request and the body read, so a stalled connection rejects — and `cachedPromise` drops the slot for a clean retry — instead of leaving the mutex wedged.

**Eager fetch**: `data.ts` starts `fetch("db.gz")` at module load (before `init()` call).

**Init**: `data.init()` loads db.gz, the idx header summary `idx/h<hdrs>.gz` (when `db.hdrs === numFinalizedIdx()`), and the latest idx pack — O(1) requests at any store size. Finalized idx packs are fetched lazily by chronIdx addressing when navigation touches them; `idxHeaders` (one `IdxHeader` per pack, latest last) powers sync counting (`countAll`), pack-skip deltas (`packHasCandidate`), and the pack-level timestamp search without any fetch. When `hdrs` lags or the summary fetch fails, init falls back to the old eager fetch-all path and peels each pack's own header (`hdrs` stays optional on the wire type — an absent value simply never equals `numFinalizedIdx()`). Tail packs are generation-named `L<tailGen>.gz` (`tailGen() = db.seq − nd`; `db.seq` normalized `??= 0` for the omitempty empty-store case) and the live delta chain rides `data/d<g>.gz`; every pack name is write-once, so all pack fetches use `cache: "force-cache"`. A non-OK response on a tail pack or delta segment means this tab's db.gz predates the backend GC grace window — `assertPackOk` triggers one `location.reload()` (sessionStorage-guarded against loops, guard cleared after a successful `init()`) and always throws so callers never touch the body. The reload is **scoped away from the background refresh**: a module-level `bgRefresh` flag is set around `refresh()`'s `applyDb` (cleared in a `finally`), and while it is set `assertPackOk` throws WITHOUT reloading — a transient tail 404 during the 5-minute heartbeat must not yank the app out from under a reading user, and `refresh()` already recovers by restoring the previous coherent snapshot wholesale and surfacing the failure through `lastRefreshError()`. Boot and user navigation keep the reload (the designed stale-tab self-heal); `refresh()` runs under `app.ts`'s `guardBg` mutex, so no user navigation can observe the flag set.

**Live content sync** (`refresh.ts`): an already-open tab silently adopts a newer store snapshot with no reload. `data.refresh()` re-fetches db.gz and, when `fetched_at`/`total_art`/`seq`/`gen` moved, re-runs the same boot body `init()` uses (`applyDb`) — every derived cache is recreated wholesale rather than diffed, then seeded from the previous snapshot wherever a position still names the same write-once object (`carryOver`: an unchanged finalized pack is never re-fetched or re-parsed for a heartbeat, while a grown tail's or a compaction's fresh stems miss by construction; the SW's own `checkManifest` purge rides this same db.gz response). On an `"updated"` result the trigger chains `search.invalidate()` → `nav.onStoreRefreshed()` (filter-stable adoption: bounds only ever rise, new/gone members join/leave, cached neighbor probes and any in-flight prefetch drop) → `refresh.publishSnapshot()`, whose `model.snapshot` write the effect table follows (the toolbar label, the reader's chrome via `nav.probeCurrent()`, `list.onStoreGrown()`, an open picker, the badge) — no content re-render, no scroll: the contract the whole feature is built to honor. Triggers: tab re-focus (60s throttle), regained connectivity, and a 5-minute heartbeat while visible — all background — plus the list's **pull to refresh** (the one manual trigger; a page reload is still the heavier one, re-fetching everything including the profile). The whole cycle runs under `app.ts`'s shared **`guardBg`** mutex (the background twin of `guard()` — same busy flag, no render/error popup, a losing caller is skipped rather than queued) so the swap can never interleave with a live navigation.

**Article loading**: `loadArticle(chronIdx)` resolves pack+offset via binary search on `IdxPack.bounds`, fetches and parses the JSONL data pack (LRU-cached by pack ID, max 20 packs).

**Neighbor prefetch** (nav.ts): after each `left()`/`right()`, the neighbor lookup (`findLeft`/`findRight` — may lazily fetch an idx pack) runs un-awaited off the critical path: its promise lands in the `next` slot keyed to that landing — this lane object, this cursor, this store, so any other state is a miss and only a membership change under an unmoved cursor (a store refresh, a ★ queue change) clears it by hand (consumed by the next keypress; a rejection clears the slot instead of failing the committed navigation) and on resolution `schedulePrefetch(target)` warms the neighbor's media on `requestIdleCallback` (`{timeout:500}`; WebKit has no rIC, so a `setTimeout(…, 200)` fallback keeps iOS/Safari prefetching instead of stalling at every data-pack boundary) — it `loadArticle()`s the neighbor, runs `fmt.extractPrefetchMedia()` over its content (final render-path URLs: resolved, bounds-checked, proxied), and warms **capped** lists: the first `PREFETCH_IMAGES` (6) images/posters as `Image`s with `fetchPriority="low"`/`decoding="async"`, and the first `PREFETCH_VIDEOS` (2) video sources as detached `<video preload="metadata">` elements (duration/dimensions/first frame — cheap for faststart assets; preload is set before src, which triggers the media load algorithm). The caps are the point: uncapped, an image-stuffed neighbor (live store has 300+-image articles) split bandwidth so thin nothing completed before the next step and competed with the on-screen article's own lazy loads. `abortPrefetch()` cancels in-flight loads by setting `src=""` (WHATWG image-update steps for `<img>`, the media-load algorithm's abort for `<video>` — removing the attribute alone wouldn't abort) and dropping the refs — but **arriving at the prefetched article itself must not abort** (`resolve()` checks `currentPrefetch.target`): its in-flight loads are what the rendered content coalesces onto, so the refs are dropped without cancelling; any other navigation aborts. The `currentPrefetch` record (also the freshness token: a pending idle callback bails when `my !== currentPrefetch`) bounds memory to one neighbor at a time. Edits to nav must preserve this abort/freshness/arrival discipline.

**Content fade-in**: double `requestAnimationFrame` for opacity transition — skipped entirely on a **slide** entry (`reader.setEntryTransition`, a committed pager drag), whose drag already was the transition.

**Service worker** (`src/sw.ts`, not `src/js/` — Parcel then emits it at the deployment root, giving it a default scope over the whole env). Offline-capable cache in five buckets keyed by mutability: `srr-assets-v1` (content-hash `assets/…`), `srr-packs-v4` (every object the manifest names — a stem is never reused, so it is cache-first UNCONDITIONALLY; only `db.gz` is network-first → cache fallback), `srr-shell-v1` (navigation network-first + content-hashed JS/CSS cache-first, runtime-cached so the worker stays hand-written and zero-dep), `srr-meta-v1` (per-root bookkeeping: the last-adopted generation `m`, the names it listed, the mount table) and the eviction-exempt `srr-pinned-v1` (offline pin). **Offline correctness is structural and is a CONSTRAINT on every edit, not a description**: a cached root names one manifest, that manifest names one set of objects, and every one of those names is write-once — so anything that advances the cached root must first cache the objects the new root's generation needs. Reconciliation on adopting a generation is ONE rule (evict what neither it nor the previously-adopted generation names), which replaced four approximate window formulas at the manifest cutover. **Full detail — the bucket policies, `checkManifest`/`adoptManifest`, the cache bound, the offline-pin message protocol, ★-Saved asset pinning and the PWA5 periodic warm: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#swts)**

**Reader render behaviours keyed to the article** (`reader.ts` `render`, around the `el.content.replaceChildren` block): the outgoing article's `<audio>`/`<video>` positions are HARVESTED before the replace and restored when you come back to it (FEB2 — `#enclosure` injects podcast `<audio controls>`, so one swipe used to kill a playing episode dead; POSITION only, never auto-resumed playback, and a `pendingRestore` WeakMap keeps a second render of the same article before its metadata lands from harvesting the still-zero value over the real one). `mediaStates` is keyed `` `<mid>:<chron>` `` — chronIdx is only unique WITHIN a mount (S38), so a bare-chron key restored one store's position onto another store's article. The five media steps around the replace run in a FIXED order — **harvest → adopt → replace → restore → rehome** — because harvest and rehome both pair state to elements BY INDEX over `querySelectorAll("audio,video")`, so adopting (which REMOVES one) before harvesting would shift every later index and misalign the whole article's saved positions. Step 3 (`replace`) now installs `buildContent(o.article, data.activeStore().base, { inert: false })` from `article-view.ts`, and `stampContentHost` applies the `lang`/`dir` stamp described next — the same two calls the pager's preview page makes, which is the whole point of them being one function each. The `harvest → adopt → replace → restore → rehome → chips` ORDER is untouched by that change and must stay so: the extraction deliberately slotted into the sequence rather than restructuring it. The content host is stamped with the article's own `lang` (the wire's `g`, from the backend's always-on detection) plus `dir="auto"` (RDR4 — otherwise everything inherits `<html lang="en">`: wrong screen-reader voice, English hyphenation patterns, undeclared-RTL rendered LTR); `.srr-content` sets `hyphens: auto`, which is only correct BECAUSE of that stamp, and an article the detector wasn't confident about carries no lang and simply isn't hyphenated.

**The mini-player** (RDR16, `player.ts` + `.srr-player`): FEB2 made stepping away non-destructive to media POSITIONS; this makes it non-destructive to PLAYBACK. The mechanism is **relocation, not reconstruction** — the live `<audio>`/`<video>` is MOVED out of `.srr-content` with one `appendChild` (an atomic remove+insert, which the HTML spec's "removed from a `Document`" steps let through because the pause check only fires when the element is *not* in a document at stable state) before `replaceChildren` would destroy it, and swapped back into its slot via `replaceWith` when you return to the owning article. Same node, same buffer: no second element, no `currentTime` handoff, no re-buffer gap — and video rides the identical path, CSS-constrained to a compact 16:9 frame (collapsed to audio's zero-width box on ≤500px phones, where the title needs the space more than a 64px cover-crop). Two concerns stay separate on purpose: **relocation is about survival** (the element moves only when its article stops being rendered), while **the bar is about control** (it shows whenever an episode is active or a queue is waiting, WHATEVER article is on screen — the episode's own included; user call 2026-09-23 retired the old hide-while-you-can-see-it rule and the `IntersectionObserver` behind it), so the transport follows you everywhere without the element ever leaping out of the prose. **The player starts FOLDED, to a floating corner circle** (user calls 2026-09-23: "hide it until a button is pressed"; a slot IN the bottom bar was built and rejected — it reflowed the article navigation, pushing "next" off centre — so the bar stays exactly as it was): while an episode or a queue exists and the view is closed, `.srr-player-dock` floats over the toolbar at the reading column's right edge — a 48px circle in the feed's colour with a progress ring (`--srr-progress`, written by the clock effect; a conic gradient hollowed by a radial mask) and three level bars that move while playing (`.srr-player-playing`). It sits in `.srr-player-dock-lane`, a pointer-transparent strip positioned exactly like the snackbar (and moved onto the reader column by the same split rules), and rides down with the toolbar when it auto-hides. Tap = open the player view; the secondary gesture — long-press, right-click, Shift+F10, wired by `dropdown.bindSecondaryPress`, the helper `bindPressMenu` now sits on — plays / pauses without opening anything. `body.srr-playing` (the container clearance and the lifted snackbar/pin lanes) follows the DOCK: set while it floats, cleared while the view covers the page. Open, the header's ✕ HIDES the view (user call 2026-09-23 — it never stops or clears anything; there is no ⌄ any more). The view is a PLACE: opening pushes one history entry (same URL, so no hashchange reaches the router) and the platform's Back — a `popstate` without that entry — closes it, while every other close path (⌄, Escape, an emptied playlist) pops the entry via an effect over `unfolded`, so it never lingers as a dead Back step. While it is open app.ts's keymap, pager commit and two-finger cycle stand down (`player.isViewOpen()` joins `overlayUp`, the picker/lightbox rule), and a stray Escape routes to `player.closeView()`; opening focuses the view itself (`tabindex=-1`), closing hands focus back to the dock. Closed is the `.srr-player-folded` CLASS (`visibility: hidden`), never the `hidden` attribute or `display: none`: the view may hold a relocated `<video>` that must stay rendered; `hidden` keeps its meaning (no player at all). The open state is in-memory only — every boot starts closed; a chip add pulses where the episode went (the Up next count with the view open, the dock otherwise). `controls` is dropped while in the bar and restored on rehome (`fmt.ts` force-sets it in content). Closing hands the position back to FEB2, so the article stays exactly as resumable as if the player had never been opened. **Media Session** publishes title/feed/album and play/pause/stop/seek handlers; `previoustrack`/`nexttrack` are registered ONLY while the playlist queue (below) is non-empty and step QUEUE items — they must never map to prev/next *article*, which would turn the lock screen into a way to skip out of the episode you are listening to (with no queue they stay unset, today's greyed-out behavior; previous follows the podcast convention — >3s in (or at the top of the list) restarts, else the entry before the current one in the playlist, so ⏮ then ⏭ round-trips; next is a no-op past the last entry). **The playlist** (the "up next" queue, same module): `injectQueueChips()` — reader.ts's step 6, after rehome — puts a `+ Playlist`/`✓ Playlist` toggle chip (`.srr-queue-chip`, a `<button>`, so the FEB2/rehome `audio,video` index pairing is untouched) after every eligible in-content media element (not the GIF idiom, and only elements with a `src` attribute — a `<source>`-only element can't be rebuilt detached, the same bar `save()` sets). Entries carry the `Persisted` shape plus mid (`{mid, chron, index, src, kind, title, feedId}`), so playing one needs ZERO pack fetches. **Entries STAY after they play** (user call 2026-09-23, "don't remove an element after played") — the list is a playlist, not a consume-on-play queue: `player/state.ts`'s `cursor` (an entry KEY `mid:chron:index`, so reorders and removals elsewhere cannot shift it) names the CURRENT entry — the one playing, or the one the play button will start — and every claim path (a press of play on a listed in-content element, a row tap, auto-advance, prev/next) just moves it. The view marks the current row in place (`.srr-player-row-now`: a tint in its feed's colour plus `aria-current`, NO label — the "Now playing"/"Up next" eyebrow was removed by user call 2026-09-23) and dims the ones before it (`.srr-player-row-played`); its row's press toggles play/pause, any other row's plays it now. Removing the current entry (`dropEntry` → `removeCurrent`) stops it if playing and makes the follower current, READY (never autoplaying). The chip menu's **Play next** inserts right AFTER the current entry (`insertNext`, a listed one MOVES); **Play now** does the same and plays it (so at the cap both are disabled for a NEW enclosure). The blob persists the whole list, the head (the playing entry) and, when nothing plays, the cursor as `c` (its index); restoring an older blob whose head sat OUTSIDE its queue puts the head back at the front. **The player controls its QUEUE only** (user call 2026-09-23): the capture-phase `play` listener claims an in-content element ONLY when its episode is queued — media played directly in an article stays the article's own (native controls, no bar, not adopted, so it stops when its article leaves the screen like any page media), and the chip menu's **Play now** routes through the queue (head-insert + `advance`) instead of calling the element's `play()`. One thing stays audible at a time: outside media starting pauses the episode (still claimed, one tap to resume), and the episode starting pauses outside media (`pauseOthers`; never the GIF idiom). **Installable (PWA)** — `src/manifest.webmanifest` (linked from `index.html`) + the SW's fetch handler satisfy the browser install criteria. `shortcuts` offers Unread (`"./#!"`, the list at [ALL] — its oldest-unread anchor) and Saved articles (`"./#!~saved"`). ⚠ **Both halves of that string are load-bearing** and neither may be "simplified" away. The `./`: a shortcut `url` resolves against the **manifest's** URL, not the app's, so a bare `"#!~saved"` resolves to `/manifest.webmanifest#!~saved` — still inside `scope`, so nothing errors, it just silently opens the raw manifest JSON instead of the reader (the bug the first cut of this shipped). The `!`: the fragment must carry **at least one character** or it collapses in the URL parse — `new URL("./#", href).hash` is `""`, not `"#"` — so the Unread shortcut written `"./#"` boots with `location.hash` empty, app.ts's init falls through to the `srr-hash` localStorage restore, and the launcher lands wherever the user last was instead of the unread list it advertises (the second cut's bug, fixed 2026-07-26). `"./#!"` is the minimum non-collapsing list hash: `hash` is `"#!"`, so the restore is skipped; `hashPos("!")` is `""` so `route()` takes the list branch, `parseHashTokens("!")` is `[]` so the filter clears to [ALL], and route's own `replaceState` canonicalizes the URL back to `"#"` — the trailing `!` never survives into history. `start_url`/`scope` are `"."` for the same deployment-relative reason as the `./`, so the same bundle installs under `/srr/` or `/srr.tmp/`. JSON takes no comments, which is why the rule lives here. ## State Machines (nav.ts)

State: `pos` (chronIdx) and `lane` (the active `Lane`, built by `makeLane(tokens)`).

**`Landing`** — how a landing is recorded, taken as a named object by `resolve`/`first`/`last`/`goTo`: `{ record?: boolean (default true), replace?: boolean (default false) }`. `record: false` is a RESUME (a filter switch, a restored `#pos`, the mini-player's jump back) — it never advances the seen frontier; `replace: true` uses `replaceState`, leaving no history entry. It is an OBJECT because these were the same two booleans in three different positional orders (`goTo` was transposed), which had `app.ts` expressing one intent as `nav.last(true, false)` beside `nav.goTo(anchor, false, true)`. `goTo`/`first`/`last` now forward the object opaquely, so they cannot transpose at all. The refactor was deferred twice for want of a compiler that would catch the migration — `make typecheck-fe` is that compiler. A landing whose store changed across its awaits commits nothing and rejects with `isStaleLanding(e)` (see ARCHITECTURE.md → Lanes).

**The lane** — active when `tokens` non-empty. `makeLane` classifies once: `[]` → [ALL] (every feed with articles); `[~saved]` → ★ Saved; a `q:` token with at most one companion → search (the companion is the RDR8 scope, at natural `add_idx` bounds); anything else → feed/tag membership, falling back to [ALL] when nothing resolves (`applyFilter`/`switchFilter` keep a KNOWN empty feed/tag scoped to itself). Unseen-only raises a membership's bounds at construction; a store refresh reconciles through `lane.refreshed()`, never a rebuild.
- `last(o?: Landing)`: jumps to the last matching article under the current filter (set the filter first via `filter.set`/`switchFilter`)
- `goTo(idx, o?: Landing)`: navigate to chronIdx; if filter active and target doesn't match, snap forward to next match; falls back to `last()` if none
- `goToArticle(chron)`: the mini-player's exact jump (`PlayerDeps.openArticle`, which also re-syncs the search bar after it — the one player path that can exit search mode) — lands on the exact chron, never a snapped neighbor: the lane keeps the landing when `isValidSeen` accepts it (true `add_idx` under unread-only, the switchFilter-resume predicate), else the filter falls back to [ALL] first, like a bare `#pos` deep link; `record: false` (returning to an episode is a resume, not a read); an unaddressable chron (expired / deleted feed / out of range) keeps `goTo`'s clamp
- `switchFilter(token)`: sets the lane, `await lane.prepare()`, acts on `lane.entry()` — a resume landing (`record: false`) or a placeholder (`notStarted` + armed Next under unread-only). A switch never advances a frontier. Decision tree: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#lanes)
- `cycleToken(dir)` (async): the next cyclable entry of `getFilterEntries()` — ★ Saved always skipped, zero-unread lanes skipped under unread-only. Detail: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#lanes)
- `cycleFilter(dir)`: `switchFilter(await cycleToken(dir))`
- `getFilterEntries()`: returns `["", "tagName", ..., "feedId", ...]` built via `data.groupFeedsByTag()`
- `getCurrentFilterKey()`: returns `""`, the single token, or `""` for multi-token filters (URL-only edge case)
- `filterLabel(key)`: resolves a filter key to its human label (`""`→"All", `SAVED_TOKEN`→"★ Saved", a `q:<query>` token→"Search: <query>", numeric feed id→`data.feedTitle`, tag name→itself) — total over every key shape nav produces, so no surface can print a raw id OR a raw `q:` token. The single source for the toolbar feed label, the document title, and the list's all-caught-up line, so none of them ever shows a raw feed id
- Navigation uses `findLeft`/`findRight` — async (may lazily fetch an idx pack); finalized packs without a filter match are skipped via summary header deltas, no fetch. `makeLane` stays synchronous
- Hash: `#pos[!tokens]` — `!` segment, `+`-separated tokens, each `encodeURIComponent`-wrapped to survive special chars in tag names.

Only real Chrome can prove it — jsdom implements neither `play()` nor `pause()`. `player.e2e.test.ts` is that argument once more for the **mini-player** (RDR16) — one ordered play → next → prev flow over real decoding audio, proving relocation keeps the same node playing (see Key Behaviors → The mini-player for what it pins and its own browser launch). `pane.e2e.test.ts` drives the desktop pane's width and visibility in real Chrome, in two layers: the CSS contract alone (the reserve derived on `<body>` from the open width on `<html>`, and what `body.srr-pane-hidden` does to it — every case there stamps the class or writes the property BY HAND, so `pane.ts` may be absent under all of it), then the real grip dragged, double-clicked and Tab-walked with the real mouse and keyboard. `a11y.e2e.test.ts` is the **automated accessibility pass** (axe-core, injected via `axe.source` and run in-page): the five single-surface states — list, reader, filter picker (default AND Info mode, which swaps every row's role and handler), settings menu and the keyboard-shortcuts card (RDR10, built entirely in JS, so nothing else reviews its roles/name) — plus **split view with the pane open and with it hidden**, which is a different a11y surface and not merely a wider one (both panes on screen at once, a two-segment toolbar rail, and a focusable `role="separator"` grip that has to carry a name and a value) — must have **zero `serious`/`critical` violations**, the regression net the hand-written roles / `aria-pressed` / `aria-keyshortcuts` / focus traps never had. It scans the whole document rather than the surface's subtree on purpose: with a popup up, a screen reader meets the popup AND whatever stayed exposed behind it, which a subtree scan would hide. Failures print rule id + impact + node targets + help URL. `minor`/`moderate` are advisory here (`region`, `page-has-heading-one` — the reader's `<h1>` IS the article title, so the list legitimately has none). ONE rule is deferred with its reasoning in-file: `color-contrast`, which traces entirely to deliberate `tokens.css` choices (`--muted` is documented there as "intentionally below AA for body text", and the source ramp/accent render on 13% tints of their own hue) — the app's `@media (prefers-contrast: more)` block clears most of it, and the rest is a design-system decision, not a test fix. Gotcha it encodes: `.srr-content` fades in over 0.25s and axe samples COMPUTED colors, so the reader audit must wait for opacity to reach 1 or every paragraph reports as a ~1.2:1 contrast failure. Second gotcha, in the split cases: `open()` navigates at puppeteer's default viewport, which is BELOW the 1000px breakpoint, and `setViewport` lands the resize before the `matchMedia` change `split.ts` listens on — so they reload and then wait on `body.srr-split` itself, never on the viewport number. Reuses the Chromium under `~/.cache/puppeteer/` (`puppeteer` pinned to 25.0.2). Gotcha: set `Connection: close` + `server.closeAllConnections()` or `server.close()` stalls on Chrome keep-alive sockets.

## Deployment

GitHub Actions `release.yml` (version tags `v*.*.*` or manual dispatch), three jobs: `verify` and `browser` (together they gate `release` — `browser` because `make verify` omits the Puppeteer layer and `ci.yml` has no `tags:` trigger), and `release` (builds the bundle with **no** cdn-url — pack base falls back to `"."` for same-origin self-hosting — tars it as `srrf.tar.gz` and attaches it plus the `dist/srr-*` binaries to the GitHub Release). There is no separate deploy job: `srrf.tar.gz` **is** the reader deploy artifact, and `srr frontend update` installs it straight into the store root next to `db.gz` — one origin serves the reader, the admin page and the packs, with an operator-run reverse proxy (Caddy + a forward-auth gate) in front — see `docs/SELF-HOSTING.md`. The hosted-Worker deploy job (`deploy-reader`, `cloud/worker/src/reader.ts`) and the Pages project that preceded it are both gone (removed with `cloud/` — a self-hosted static origin needs neither). `SRR_CONFIG_INLINE` is no longer read anywhere in `release.yml` (only `cron.yml`'s fetch job still uses it).
