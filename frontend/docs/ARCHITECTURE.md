## `data.ts`

CDN data layer: fetches `db.gz`, then the idx header summary (`idx/h<hdrs>.gz`) + the latest idx pack + the **live delta chain** only (`fetchDeltas`: `data/d<g>.gz` for `tailGen < g ≤ seq`, parsed into the RESIDENT `deltaArts` — each segment is one dirty cycle's whole batch as data-pack JSONL, so chrons ≥ `tailCovered()` = `total_art − na` resolve idx entries, meta cards, AND content from it with zero pack fetches; the `na` cross-check fails loudly on a mismatched chain, and every segment passes `isLatest=true` so a GC'd-under-a-stale-tab chain takes the guarded reload). Exports `tailGen()` (`seq − nd`, the tail packs' generation — every latest-name fetch uses `L<tailGen>`, not `L<seq>`), `tailCovered()`, and `deltaArticles()` (search.ts's overlay input); `buildLatestIdx` synthesizes ONE logical latest pack (physical `L<tailGen>` header ‖ entries ‖ spliced delta feed-ids ‖ verbatim footer — an all-delta store, `tailCovered()==0`, gets a zero header) so counting/nav code needs no seam awareness, while `loadArticle`/`loadMeta` short-circuit delta-region chrons to the resident chain — resolved via `await deltaLoad` (the in-flight/resolved chain promise for the installed db), NOT the sync `deltaArts` array, because `applyDb` installs the new db and only repopulates `deltaArts` after several awaits, so an unguarded caller reading a delta chron in that window would otherwise hit `[]` and throw — and `getPackRef` hard-throws on them (the structural seam guard — its bounds end at the last real data pack). Finalized idx packs load lazily on first touch (`fetchIdxPack`, promise-deduped slots) with eager fetch-all as the fallback when `hdrs` lags or the summary 404s. Fetches JSONL data packs on demand (LRU-cached by pack ID; `loadArticle` resolves pack+offset via binary search on `IdxPack.bounds` and fetches inline — `loadDataPack` is inlined into it). Exports `db`, `init`, `refresh()` (returns `"unchanged"` or `"updated"`; the re-runnable boot: re-fetches db.gz and, when `fetched_at`/`total_art`/`seq`/`gen` moved from the resident snapshot, re-runs the shared `applyDb` boot body — every derived cache (idx fetch slots, data/meta LRUs, `groupFeedsByTag` cache, `idxHeaders`, `expiredCounts`) is recreated wholesale rather than diffed, since a `gen` change would discard it all anyway and refetches ride the SW/HTTP cache; called by `refresh.ts`), `loadArticle(chronIdx)`, `fetchPackBytes(path, isLatest)` (generic pack fetcher used by `search.ts` and the meta/ loaders; `isLatest=false` so a missing meta pack never triggers the guarded reload — that path is upstream-gated by `metaReady()`), async `getFeedId(chronIdx)`/`findLeft`/`findRight`/`countLeft`, sync `countAll` (latest pack + its cumulative header) — both counts thread `expiredCounts` (a per-slot `Uint32Array` built in `init()` from each feed's `xp`) into `IdxPack.countLeft`'s header-shortcut subtraction, so expired articles never inflate badges/counts, `numFinalizedIdx()` (the idx finalized-pack formula), `numFinalizedMeta()` (meta finalized-pack formula, shared with `search.ts`), `metaReady()` (true when `mp·5000 + mt + na === total_art` — shards + tail cover the consolidated region, the resident chain the rest; gate for both list-from-meta and search), `loadMeta(chronIdx)` (returns `IMetaWire` card: delta region from the resident chain first, then `db.head`, then meta/ when `metaReady()`, else the `data/` fallback — so the home list never breaks while SyncMeta lags), `parseJsonl<T>(buf)` (shared JSONL decoder used by meta/ loaders), `feedTitle(feedId)` (display title with the `"[DELETED]"` tombstone fallback), `groupFeedsByTag(includeEmpty = false)` (no separate `activeFeeds` helper — the active-feeds logic is folded directly in; the default drops `total_art === 0` feeds, `includeEmpty` keeps them — the picker passes `!isUnreadOnly()` so empty feeds show when read items are; cached per-flag). Re-exports `IDX_PACK_SIZE`, `META_PACK_SIZE`; all pack fetches resolve against base.ts's `PACK_BASE`, so pack addressing and content-URL resolution share one base.

## `nav.ts`

**The facade plus the filter / search / navigation core.** Since ENG3 the seen-frontier, ★-Saved, media-prefetch and hash-grammar concerns live in `seen.ts` / `saved.ts` / `prefetch.ts` / `route.ts`; nav re-exports their public names **unchanged**, so every consumer, every test and all the contract prose in this row still reads `nav.*`. What stays here: the `filter` state machine, the search snapshot, the traversal/resolve path, and the reconciliation seams. Navigation state machine: hash routing (`#pos[!tokens]`), traversal, filtering. Returns `IShowFeed`. Uses `pushState`/`replaceState`. Tokens are feed IDs or tag names. Exports `filter`, `fromHash`, `left`, `right`, `first`, `last(replace = false)` (no `token` param — set the filter via `filter.set`/`switchFilter` first), `switchFilter`, `goTo`, `select` (set the cursor to an exact, already-known-matching chronIdx — the list's keyboard selection; no feed walk / idx fetch, no hash update or `recordSeen`, since moving the cursor isn't reading), `cycleFilter`, `cycleToken(dir)` (async: the next **cyclable** filter-entry token relative to `cycleOriginKey()` — `cyclableLanes` skips ★ Saved always and, in unread-only mode, tag/feed lanes with 0 unread (`[ALL]` always survives), so the cycle lands only on lanes worth reading; `cycleFilter` is `switchFilter(await cycleToken(dir))`; the list's `app.onCycle` uses it too), `currentFeedId()` (feed id of the article currently in the reader, -1 = none), `getFilterEntries`, `getCurrentFilterKey`, `filterLabel`, `pruneSeen` (also prunes orphaned `srr-seen-ts` keys), `unreadCounts`, `tagUnreadFromCounts`, `isUnreadOnly`, `setUnreadOnly`, `markAllRead`/`markUnreadFrom` (the explicit frontier gestures — below), `pendingFrontierUndo`/`markFrontierUndoOffered`/`frontierUndoSize`/`undoFrontierMove`/`clearFrontierUndo` (RDR1/RDR2 — one step of reversibility for the frontier RAISES: `recordSeen` and `markAllRead` snapshot the keys they moved, `frontierUndoSize` measures the move through the SAME tally the badges use (so the number app.ts reports is the number the badges lost), and `undoFrontierMove(u)` writes the frontiers back through `writeSeen` — refreshing the per-key `st` stamps to NOW, since only a newer stamp makes profile.ts's per-key LWW propagate a lowering; a key that did not exist is restored as `-1`, markUnreadFrom's precedent. **The offer is asked once per raise**: app.ts asks on every render, but a render that moved no frontier of its own (a step BACKWARDS, a filter switch, any read in the peek modes — which never raise at all) leaves the previous snapshot in place, so `pendingFrontierUndo()` returns null once `markFrontierUndoOffered()` has closed it — called whether or not the offer cleared app.ts's size threshold, since a move too small to mention is still one already considered. The snapshot deliberately OUTLIVES the offer, and `undoFrontierMove` takes it as an **argument** rather than reading the latest: the snackbar is answered seconds after it appears, and a raise landing in between must not re-point the button at a different, smaller move than the one whose size it announced. The explicit rewind is deliberately NOT undoable — that gesture IS the undo), `setSavedHook` (the saved-set transition seam both save paths — the reader star and the list row — pass through; app.ts uses it for FMT2a asset pinning, since talking to the SW is not nav's job), `neighborOlder`/`neighborNewer` (the strict prev/next-of-a-member seam: saved → save-index step, feed/search → the value seam `feedLeft`/`feedRight`), `isSaved`/`toggleSaved`/`savedCount`/`currentChron`/`anchorChron` (the reader's `pos` when it still matches the active filter, else -1)/`listAnchor` (the **list** anchor, and — since `render` selects it — the row the list highlights on a fresh filter: `anchorChron` when the reader's article still matches, else a feed/tag/`[ALL]`'s **oldest unread** article (the start of the unread backlog, to read forward from) computed by raising each member's bound past its seen high-water and taking the oldest match, falling back to -1 = newest when nothing is unread (`[ALL]` runs the same scan across every feed — `filter.clear` populates `filter.feeds` with all of them — so a fresh device lands at the oldest article overall, like a never-opened tag); ★ Saved anchors at the **front of the queue** — its earliest-*saved* article (`savedOrder()[0]`, save order not chronIdx), the read-later queue consumed front-to-back, read forward toward newer saves (-1 only when nothing is saved); search (and an empty store) is always -1 = newest — a query always shows its newest hit regardless of seen state) and `SAVED_TOKEN` (saved articles), and `SEARCH_PREFIX`/`isSearchFilter`/`searchQuery`/`searchScope`/`searchTruncated`/`searchAvailable`/`searchShort` (the search filter mode — below; `searchScope()` is the lane a query is scoped to, `""` when it spans the store), plus `hashPos(hash)` (the position part of a `#pos[!tokens]` hash — everything before the first `!`; `parseHashTokens` is the suffix half. app.ts's `route()` and boot foreign-hash guard both classify through it). `unreadCount(ch)` = the feed's articles strictly after its `srr-seen` position (on each read — Right, or opening a list row (`goTo`), but **not** a filter switch or a reload/restore (`switchFilter` and `fromHash` both resolve with `record: false`, so switching lanes or reloading the page never consumes unread — only reading forward does) — `recordSeen` raises the seen frontier of **every feed in the active filter** — the shown article's own feed included — to `pos`, a **one-way raise everywhere**: opening an article marks all OLDER articles across the list seen, reading the newest in [ALL] clears every count, and stepping BACK to an older article re-reads it without un-marking anything — read progress only rewinds through the explicit gesture below. Every seen write also stamps that key's `srr-seen-ts` ordering timestamp (`writeSeen`) so sync can order it per key. Search/`q:` mode and ★ Saved are both **peek modes** that `recordSeen` exempts wholesale — it returns before touching any feed's frontier for either, since peeking at a hit or an archived item isn't resuming its feed). **The explicit frontier gestures**: `markAllRead()` raises every filter member's frontier to the store's newest chron (the same foreign-chron high-water `recordSeen` writes — a pure raise, trivially sync-safe) and `markUnreadFrom(chron)` — the ONE path that lowers a frontier — marks everything from `chron` (inclusive) to the latest unread across the filter by lowering each member's frontier to `chron−1` (members already below stay; `chron` 0 stores `-1`, the never-seen equivalent, keeping the key so its `srr-seen-ts` stamp outranks older raises on other devices). Both skip peek modes, return whether anything changed, and `pushSoon()`; both sides of the subtraction are idx-derived (`countAll` − `countLeft(seen+1)`) so db.gz `total_art` drift can't skew it; a feed never seen on this device counts as fully unread (its full backlog — `countAll`, a sync no-fetch count), so a fresh device badges every feed and the row badges sum to their tag header. A tag has no count of its own — the dropdown (`tagUnreadFromCounts`) sums its member feeds' `unreadCount`s onto the tag header. A **tag also has no stored seen position of its own**: `getSeen(tag)` derives it as the *oldest* read (min chronIdx) of the tag's member feeds, the anchor `switchFilter(tag)` resumes at, so opening a tag lands at its least-recently-read member and every unread article in the tag sits to the right (none skipped on the left). `pruneSeen` drops any legacy `tag:` key (tags stopped storing their own position). **Unseen-only mode** (`isUnreadOnly`/`setUnreadOnly`, persisted in `srr-unread-only`; device-local, not in the hash) applies to **every filter** ([ALL]/single feed/tag) — the one-tap catch-up view: when on, `filter.applyUnseen` (shared by `set` and `clear`, so it covers [ALL] too) raises EACH filtered feed's lower bound to `max(add_idx, seen+1)` (snapshotted at apply time, so the nav set is stable as you read this session), so `findLeft`/`findRight`/`matches`/search skip already-seen articles. The "member" wording below generalises from tags to whatever feeds the filter spans. The tag still opens at its **current position** — the resume anchor `getSeen` returns (its least-recently-read member, same as outside unseen-only), NOT its oldest unseen: `isValidSeen` validates that resume position against the true `add_idx` rather than the raised bound, so the raised bounds skip seen articles on Left/Right without bouncing the open forward. From the resume position, Right steps onto the first unseen — and the entry stays reachable: `resolve` records any landing the raised bounds don't cover (the resume position, a restored/shared `#pos`) as **`filter.anchor`**, which `feedLeft`/`feedRight` slot into their walks so the navigable sequence is `{entry anchor} ∪ unseen` — ← returns to the first article shown instead of dead-ending, the anchor renders as a (read) list row, and `anchorChron` accepts it so back-to-list lands on it. Navigation-only (it does NOT make `matches()` true, so unread counting/badges ignore it); reset whenever the filter is re-applied (`set`/`clear`). `has_left`/`has_right` are computed by neighbor probes — `neighborOlder(pos)`/`neighborNewer(pos)` with `.catch(()=>-1)` so a cold-pack blip degrades to a disabled button rather than an error popup. The dropdown badge stays in lockstep: `feedUnread` (so `unreadCount`/`unreadCounts`/`tagUnreadFromCounts`) is the plain live unread — a feed's articles strictly after its seen position. Reading is accounted on ENTER: `recordSeen` marks the open article seen the instant you land, so it leaves the badge immediately — there is no pad holding the current article as still-unread until you step off it. That keeps the badge in agreement with the reader's `pendingRight` pill — the same tally body (`tallyWith`) with each frontier floored at the cursor, identical on every recorded landing — and the list's per-row read/unread dots (`isRowUnread`), which already treat the current article as read — and it means **switching filters never moves a count**: the switch lands on an already-seen resume article and records nothing (`switchFilter` resolves `record:false`), so only reading forward changes the number. **Search filter mode** is a third explicit-set mode beside feed-membership and ★ Saved: when a token is `q:<query>` (`SEARCH_PREFIX`) — alone, or (RDR8) beside exactly ONE feed/tag token, its **scope** — `filter.search` is set and navigation walks an explicit set of matching chronIdxs — the title-search hits — like ★ Saved walks the saved set, except search order IS chronIdx order so it rides the value seam `feedLeft`/`feedRight` directly (`matches`/`showFeed`/`neighborOlder`/`neighborNewer` all branch on it, so **the list and the reader walk it for free** with no extra plumbing). The set is computed once per query by `search.loadHits(term, SEARCH_CAP=500)` (cached in `search.ts` via `cachedPromise` keyed by query string, so concurrent walks within one render dedupe); nav keeps only the snapshot (`searchSorted`/`searchSet`/`searchCards`) and the supersession guard in `ensureSearchSet` — a late-resolving keystroke can't overwrite fresher hits. **The snapshot's identity is the query AND the scope** (`searchKey()`, a JSON of both): re-scoping the same query re-derives a different hit set, so it invalidates exactly as a new query does, and the supersession guard compares that composite. `searchTruncated()` flags the cap. **Scoped search** (RDR8, `filter.scope` + `searchScope()`): the scope token resolves to `filter.feeds` exactly as a plain feed/tag filter does but at NATURAL `add_idx` bounds — never `applyUnseen`, since search is a peek mode and a query inside a lane must still find its read articles — and nav hands that map to `search.loadHits` so the INTERSECTION happens inside the scan (see `search.ts`), never over the capped hit list. An UNSCOPED query keeps `filter.feeds` empty (feed-agnostic like ★ Saved); a scope that resolves to no feeds honestly finds nothing rather than silently widening; a third token is not a scoped query at all but an ordinary multi-token filter. `membershipTokens()` is the one rule for "which tokens does this filter resolve membership from", shared by `filter.set` and `onStoreRefreshed` (so a scoped query's bounds reconcile after a refresh like any lane's, while the feed-agnostic modes are skipped). Both are still peek modes: `frontierScope().peek` is `filter.search`, scope or no scope. The query rides in the shareable `#!q:<query>[+<scope>]` hash like any token (reload/back/forward restore it; `tokensSuffix` escapes a literal `+` in the query to `%2B` so the `+`-separator split survives), and it behaves like a tag filter — picking another filter / two-finger cycle / arrow-cycle leaves it (search is **not** in `getFilterEntries`, so you can't cycle *into* it). `switchFilter`/`last` open it at the newest hit; `fromHash` loads the set before validating a `#pos!q:…` deep-link so the position is honored. The UI (toolbar magnifier + pinned search bar) lives in `app.ts`. `resolveMembership(tokens)` is the ONE token-resolution rule shared by `filter.set`, `filter.clear`, and `onStoreRefreshed` — numeric token = that feed, else a tag's members, only feeds with `total_art` join — so a mixed feed-id+tag filter resolves identically everywhere it's computed. `onStoreRefreshed()` reconciles the filter after `data.refresh()` swaps in a newer snapshot, WITHOUT re-snapshotting the walk: each member's bound only ever rises (a grown `add_idx` from expiration, never re-derived from seen — that would yank the unseen-only sequence mid-session), a brand-new member (a new feed under [ALL], a feed newly tagged into the active filter) joins with the same bound a fresh `set()`/`applyUnseen` would give it, and a member gone from the store leaves; `pos` is untouched (chronIdx is a permanent address) and saved/search skip the per-feed bound work entirely (their membership is an explicit set, not `filter.feeds`). It also drops the cached neighbor probes (`next.left`/`next.right`) and aborts any in-flight prefetch — both stale for content that just changed — and for an active `q:` filter drops and reloads nav's own search snapshot (the caller, `refresh.ts`, invalidates `search.ts`'s caches first; `ensureSearchSet`'s supersession guard absorbs a concurrent query change racing the reload). `probeCurrent()` recomputes the reader chrome (`has_left`/`has_right`/`right_count`) for the article already on screen after a refresh, without re-rendering content or scrolling — `data.loadArticle(pos)` is cache-warm, so this costs at most an idx/meta probe; `app.ts`'s `refreshAfterStore` uses it for the silent-refresh contract.

## `list.ts`

The **list surface** (home): a scannable headline feed that is a **bidirectional infinite window anchored at the filter's reading position** (`nav.listAnchor()`) — opening it drops you back at the article the reader last sat on (when it still matches), else a feed/tag/`[ALL]`'s **oldest unread** article (the start of the unread backlog, to read forward from, with the already-read older rows below it — `[ALL]` runs the same scan across every feed), else ★ Saved's **front-of-queue** article (its earliest *save* — save order, not chronIdx — the read-later queue consumed front-to-back), else the newest (search, an empty store, or a feed/tag/`[ALL]` with nothing unread). Newer ("next") articles page in **above** the anchor and older ones **below**. **Read amplification win:** the list reads thin `meta/` cards (`data.loadMeta`, `IMetaWire {f,w,t}`) for each row instead of full `data/` records — O(meta-pack) network cost for the home list, not O(data-pack). When `metaReady()` is false (SyncMeta lagged), `loadMeta` falls back to `data/` transparently, so the list never breaks. The full `data/` record is only fetched by `loadArticle` when a row is opened in the reader. **Anchor positioning:** the anchor row is **centered in the viewport on every list arrival** — reader return, filter change, boot — with context above and below, and the current article carries `.srr-row-current` (a source-tinted wash; the colored rail already marks the left edge) so you land back on it; `scrollChronToView(chron)` does the centering via `window.scrollTo` (clamped, so a near-edge anchor lands as close to centered as the content allows). The `anchorNow` arg (set in app.ts when `view` was `"reader"`) only decides **when** that scroll commits: a reader-return anchors immediately (its pack is warm from the article on screen), while a fresh anchor takes land-once. **Land-once for a fresh anchor (`landOnceMode = anchoredMid && !anchorNow`):** a fresh anchor (boot/filter change) would otherwise scroll onto still-skeleton, pre-font rows and then **bump** as `content-visibility` paints and web fonts reflow them taller. So it stays at the top during load (and **holds the `IntersectionObserver`** so the top sentinel can't runaway-page newer rows), then lands ONCE, centered the same way: after `document.fonts.ready` it CONVERGES the measurement without moving — each frame re-pins every row's true height and recomputes `chronScrollTarget(seed)` — and only when that target stops changing (layout settled, bounded ~20 frames) does it `scrollChronToView` a single time and start the observer. Opening the reader while this is pending cancels the commit: the list's container (`el.listView`, hidden by `showReader()`) is checked in both `commit()` and the settle loop, so once the reader is the visible surface the deferred scroll is skipped — leaving the reader's own landing position alone — while the observer still starts, so infinite scroll is live when the list returns. The per-fill `reassertAnchor` runs only for the immediate-anchor reader return. The highlight is set per row in `rowEl` and re-derived in `refresh()`, keyed on `nav.currentChron()`. Owns no nav state — its `walk` steps `nav.neighborOlder`/`neighborNewer` from a member seed (feed/search = the chronIdx value seam over `nav.filter.feeds` / the hit set; saved = a save-index step over the insertion-ordered set), an unbounded reader walk in both directions, so the rendered rows ARE literally the reader's prev/next sequence under every mode (feed/tag/unseen-only/saved/search). **The scroll seam**: every scroll read/write in this module goes through the module-level `sc` (a `scroller.ts` `Scroller` — window below the split breakpoint, the pane element in split), swapped by `app.ts`'s `setScroller()` on init and on every breakpoint crossing; the IntersectionObserver's `root` is `sc.root()` (`null` = viewport) so the sentinels page correctly against whichever box is actually scrolling, and `stickyOffset()` reads the search bar's presence via `getClientRects()` rather than a cached flag so it agrees with `sc` after a crossing. In split view, `followCursor()` is the reader-pane step's list-side echo — see the module row below and "Two surfaces + two popups" above. Reads `nav.getSeenMap`/`nav.isRowUnread` for the per-row read/unread weighting + `nav.isSaved` for the star. Newest-first rows (`<a href="#chron!tokens">`, click intercepted → `onOpen` since `<base target=_blank>` would new-tab a real hash link) showing a source-colored rail (`data-src`, `fmt.srcColorIndex`) + a colored mono "source · age" eyebrow over the title + a tappable save star (`.srr-row-star`, toggles `nav.toggleSaved` in place — in the Saved view, un-saving removes the row). **Term highlighting (RDR8)**: in search mode the title goes through `paintTitle`, which wraps `search.matchSpans`' raw-string ranges in `<mark>` — element building plus text nodes, NEVER `innerHTML` (a title is untrusted feed content), and outside search mode it is exactly the `textContent` write it replaces. The `<mark>` styling is color-only on purpose: a weight or size change would reflow the row and break the pinned intrinsic heights. **Row swipe actions (RDR14)**: a one-finger horizontal swipe on a row acts on THAT row — → toggles ★ Saved (`toggleRowSave`, the star's own body, shared so tap and swipe can't drift), ← toggles read. The touch machine and the axis lock are `gestures.ts`'s (`setRowSwipe`, registered by `setup` alongside the pull); what lives here is the row resolution (`closest("a.srr-row")`, so the pill/dividers/termini/empty state are not rows), the affordance and the two actions. The affordance is a `--swipe` custom property translating the row's CHILDREN while the row box stays put, revealing a `::after` glyph at the edge the finger came from (`✓`/`↺`/`★`/`☆` — always the OUTCOME of releasing) — so the row keeps the layout box whose real height `pinHeights` measured (a swipe can never shift the scroll) and `transform` on the row itself stays free for the keyboard edge bump. `swipeAction(row, dir)` returning null is how an unavailable direction declines: the row simply doesn't move in the peek modes (★ Saved/search never touch a frontier) or on a still-skeleton row (read state is per FEED and its feed hasn't landed). **The read toggle is a single-feed frontier move**: mark-read goes through `seen.recordSeen` with an EMPTY `FrontierScope.members` — the raise primitive with the row's own feed and nothing else, where OPENING the row raises the whole navigation list — and mark-unread through `seen.markUnreadFrom` scoped to that one feed. It **rides S57's undo**: the frontier model has no per-article read bit, so marking an old row read consumes its feed's backlog, and "swipe back" as `chron−1` would leave that backlog read for good — so the mark-read swipe keeps the `FrontierUndo` snapshot `./seen` took of its own raise (answering the undo offer right there via the injected `menus.offerFrontierUndo` — `list.setup`'s fifth arg, injected rather than imported so no `list`↔`menus` cycle forms — instead of leaving it for a READER render another surface and minutes later; the offer marks the slot itself and applies its own `UNDO_MIN_ARTICLES` bar, so an ordinary one-row swipe stays silent while a swipe far ahead of the frontier gets the same "Marked N read · Undo" snackbar the reader's gestures get, which is the point: that swipe reads everything behind the row too) and the inverse swipe restores it verbatim via `nav.undoFrontierMove`, **guarded on the live frontier still being exactly where the swipe left it** (anything else — reading in between, a sync merge — falls back to the explicit rewind, which would otherwise un-read what was read since). A commit ends in `refresh()` and deliberately NOT a rebuild: under unread-only the membership moved, but re-snapshotting it would pull the ground out from under a gesture aimed at one row, so the swiped row greys in place exactly as a row read in the reader does on return, and the membership re-derives on the next natural rebuild. Known gap: the RDR12 unread badge/tab-title readout is app.ts's and re-syncs on the next landing/refresh, not on the swipe itself. A committed swipe also arms `swipeClickGuard`, cleared by the click it swallows or by the next `touchstart`, so the finger-lift can't open the reader while a real tap right after still does. The list's **time axis** is sticky day-strata dividers (`.srr-day-divider`): `relabelDividers()` rebuilds them after every render/page by walking the rendered rows and inserting a `fmt.dayLabel` marker (TODAY/YESTERDAY/`WED 27 MAY`) before the first row of each day — run inside `fetchNewer`'s scroll-compensation bracket so any divider add/remove rides the same viewport-anchored compensation, suppressed in search **and ★ Saved** mode (both cross-time explicit sets), and skipped by the keyboard cursor's `rowSibling`. The list caps **both ends** with matched sign-offs: `syncBottomTerminus()` appends an "OLDEST" sign-off (`.srr-wire-end`) once the downward walk is exhausted (`exhaustedBottom`, from `render`/`fetchOlder`), and `syncTopTerminus()` prepends a "LATEST" sign-off (`.srr-wire-top`) once the upward walk is exhausted (`exhaustedTop`, from `render`/`fetchNewer`). `syncTopTerminus(compensate)` keeps the viewport put across the prepend on the incremental `fetchNewer` path (the same scroll-compensation `fetchNewer` does for its prepended rows) by measuring the shift with `sc.extent()` — the scroller's own scrollable length (`scrollHeight`, window or pane), so the compensation is correct whichever box `sc` names; both are idempotent, cleared on rebuild, and skipped by `rowSibling` so they never intercept cursor stepping. Exports `setup(el, onOpen, onScroll?)` (`onScroll` resyncs the gesture toolbar baseline after a programmatic scroll; `setup` also registers the surface's two gestures — **pull to refresh** via `gestures.setPullRefresh(container, () => refresh.refreshNow())` and the **row swipe actions** via `gestures.setRowSwipe(container, spec)` — the touch machine is gestures', but the surface and the actions are the list's, so the wiring lives here rather than in app.ts's `setupGestures` call), `render(anchorNow?)` (full rebuild anchored at `nav.listAnchor()`, centered; `anchorNow` commits the centered scroll immediately instead of land-once. When the filter resolves to a **specific** article — the `anchoredMid` seed, a fresh feed/tag/`[ALL]`'s oldest-unread position — it also makes that the **current selection** via `nav.select`, so updating the filter highlights the row the reader would open: one shared cursor across both surfaces. The live-reader return is a no-op (already `pos`); the newest-default anchor (`-1`: search, an empty store, or a caught-up feed/tag/`[ALL]`) stays unselected so the first arrow establishes the cursor and a caught-up `[ALL]` shows nothing selected. **Under split a rebuild does not claim that cursor at all** (`mayClaimCursor`): the pane and the reader share `nav.pos`, and re-seeding it from the list's own anchor while the reader holds an article left the two panes naming different articles — the toolbar arrows then stepped from the highlight rather than from what was on screen (a Show-read flip jumped 20 → 25; a search keystroke left them inert). Explicit navigation still moves it. `renderSearch` selects the newest hit for a query), `refresh()` (re-derive dots/stars + the `.srr-row-current` highlight from live state, no scroll), `show(anchorNow?)` (**the expandable-list efficiency seam**: when the reader's article is already a rendered row — the common return path after stepping a few within the window — re-anchor by *scrolling to it* (centered, like every anchor) with no feed walk / no fetch / no rebuild; a filter change or an article outside the loaded window falls through to a bounded rebuild that forwards `anchorNow`), `followCursor()` (split view only: the cheap cousin of `show(true)` for a reader-pane step that stays inside the loaded window — re-derive row state via `refresh()` and scroll the cursor row into the pane's live band via `scrollRowIntoView`, no centering and no rebuild; a cursor that stepped outside the window falls back to `show(true)`'s bounded rebuild), `rerender()` (force rebuild after an unseen-only flip / search-query change), `invalidate()` (drop the built-window claim so the NEXT `show()` takes the rebuild path — for actions that change the filter's membership while the list is hidden behind the reader, e.g. `markUnreadFrom`/`markAllRead` re-raising the unseen bounds; rebuilding a display:none list immediately would pin zero row heights), `loadMore()` (next older batch, append) / `loadNewer()` (next newer batch, prepend; both for the IntersectionObserver and tests), `moveSelection(dir)` (the **keyboard selection cursor**: A/←=older neighbor, D/→=newer, stepping the `.srr-row-current` highlight over the rendered feed — which IS the filter's order, so the neighbor is just the adjacent row, no walk — and syncing `nav.select`/`nav.pos`; pages the window when stepping past the loaded edge, then scrolls the selection into view clear of the **bottom-fixed toolbar** (`scrollRowIntoView` reserves `toolbarInset()` so a downward step isn't parked behind it); with no cursor yet the first key drops it on the topmost visible row; at the genuine start/end of the feed it `bumpEdge`s the row — a directional rubber-band cue, honoring `prefers-reduced-motion` — instead of silently no-op'ing). `onStoreGrown()` is the store-refresh reconciliation `app.ts`'s `refreshAfterStore` calls when the list is showing: a probe-first anti-flicker check (`neighborNewer(newest)`, no state touched until it resolves) decides whether anything newer actually arrived before silently reopening an exhausted top — `refresh()` first re-derives row state (covers a gen-rebuild's changed feeds; can itself collapse an empty Saved view, in which case there's nothing left to reopen), then, only if the top was exhausted and the probe found a newer match, it clears `exhaustedTop`, resyncs the "LATEST" terminus, and re-`observe`s the top sentinel — IntersectionObserver only fires on intersection CHANGES, and at the parked-at-top scroll position the sentinel is already intersecting, so removing the terminus alone wouldn't re-trigger `fetchNewer`'s normal paging path; a `growing` re-entrancy guard drops a second concurrent call. That silent reopen is the one thing a reader could not otherwise notice, so it also opens the **"↑ N NEW" pill** (`paintNewPill`/`resetNewPill`): a `position: fixed` overlay button — never in flow, because the no-jank prepend contract above forbids moving what the user is looking at — carrying the count `fetchNewer`'s prepend already produced (consumed, never re-derived; counting stays in `nav`). It shows only inside the window a store-grown reopen opens (`grownRunway`, cleared when the top re-exhausts), so ordinary upward paging stays silent; tapping smooth-scrolls to the top (instant under `prefers-reduced-motion`) and dismisses, as does reaching the top organically, a rebuild, an empty-state collapse or a top-side `trimWindow`. Search mode is exempt (an explicit result set, and the pinned search bar owns that strip). Known gap, deliberate: arrivals landing while the top edge is already open aren't signalled — there is no cheap count for them and the pill must not invent one. Virtualized via CSS `content-visibility:auto` (offscreen rows skip layout/paint) + infinite scroll in both directions: top + bottom sentinels observed by one `IntersectionObserver` (`pump` fills the viewport downward; the top sentinel pages newer rows in, prepending with manual scroll compensation — `.srr-list` sets `overflow-anchor:none` so the browser doesn't also adjust; jsdom lacks IO so `render` lays the initial window and `loadMore`/`loadNewer` page it). Every loaded row (initial render, older append, newer prepend) is rendered once to measure its true height, pinned as its `contain-intrinsic-size`, then handed back to `content-visibility:auto` (`pinHeights`) — otherwise an offscreen row keeps the 4rem placeholder until it scrolls into view, then corrects to its real height, and with `overflow-anchor:none` that resize above the viewport jumps the scroll (the upward-scroll jump). The pinned value is the **content-box** height (`offsetHeight − vertical padding − border`), because `contain-intrinsic-size` sizes the content box while `offsetHeight` is the border-box — pinning the border-box made each skipped row reserve ~19px too much and over-scrolled the compensation. `fetchNewer`'s prepend then compensates by how far a row **in the viewport** actually moves (anchor `getBoundingClientRect().top` delta → `window.scrollTo`), not by a `scrollHeight` delta or the topmost row, so day-divider churn or any change not directly above the viewport can't lurch it. **Windowed DOM (`trimWindow`)**: the loaded row set is bounded — after each page-in the far side is recycled (`fetchOlder` → trim the top, `fetchNewer` → trim the bottom). Rows were previously never removed, so a deep walk through a 50k+ `[ALL]` lane accumulated tens of thousands of nodes (`content-visibility:auto` caps PAINT, not memory) and every page-in walked ALL loaded rows in `pinHeights` + `relabelDividers`, so paging cost grew with scroll depth (measured on the stress store: 2,460 rows and 31.9 ms → 114.2 ms per page across an 80-batch walk; with trimming, 90 rows and a flat 25.9 → 19.6 ms). The budget (`rowBudget`) is derived from the MEASURED mean row height — `WINDOW_VIEWPORTS` (7) screens, ~3 each side of the viewport — not a fixed count, so dense and roomy layouts keep the same SCROLL distance of buffer; that distance is load-bearing, since it must comfortably exceed the IntersectionObserver's `ROOT_MARGIN` or a trimmed edge would put its sentinel straight back in range and re-trigger the paging that refills it (thrash). Where heights aren't measurable (jsdom) it falls back to the fixed `MIN_WINDOW_ROWS` (`BATCH*3`). A trimmed edge is **re-pageable, never exhausted**: `exhaustedTop`/`exhaustedBottom` is CLEARED and its terminus removed, the paging cursor (`newest`/`oldest`) moves to the surviving edge row, and scrolling back re-materializes the rows through the existing `rowEl`/`fillRow` paths. A top trim shifts content up, so it compensates exactly like `fetchNewer`'s prepend — by how far a row that is actually IN the viewport moves (anchor picked among the SURVIVORS), never by a `scrollHeight` delta. Regression net: `e2e/stress/reader.stress.test.ts`'s "stress: list DOM window" (bounded node count after ≥2,400 rows paged, plus the flat-cost-vs-depth timing). One freshness token (`tok`) invalidates in-flight loads on rebuild, mirroring dropdown's fill tokens.

## `gestures.ts`

Touch and scroll handlers: one-finger horizontal drag = the reader **pager** or a list **row action** (both below), one-finger downward overscroll on the list = pull to refresh, two-finger vertical swipe = step the filter (via `deps.onCycle`, which app.ts makes surface-aware), scroll-down hides toolbar — except through the last bar-height of the page, where the bar instead rises 1:1 with the scroll like a page footer (an inline scroll-linked transform; a 150ms settle timer seats the bar under its normal transition when the gesture stops mid-zone, else it would park half-sunken below the screen edge). `setupGestures({ toolbar, onCycle })` returns `Gestures` with `resetScroll()` (app wires it into `list.setup`'s `onScroll` so the list's anchor jump / prepend compensation resyncs the scroll baseline and reveals the toolbar — a programmatic jump would otherwise read as a downward scroll and hide it; app.ts's `scrollReaderTop` also calls it after the reader's own `scrollTo(0,0)` on **every** article/empty-state render, so the bar is revealed on arrival instead of leaking the previous article's hidden state — the reader can't lean on the incidental `scrollTo(0,0)` reveal event, which doesn't fire when already at `y=0` and is coalesced / mis-read on mobile, leaving the bar stuck hidden with no way to scroll up past the top to bring it back). Landing position is `scrollReaderTop`'s alone: the focus move into the reader right after (`render`/`renderEmptyReader`) uses `focus({preventScroll: true})`, so a tall titleless article's now-focused body can't itself re-scroll the masthead off top. **`GestureDeps` no longer carries `goPrev`/`goNext`**: the blind `touchend` swipe that measured `dx >= 50` and fired prev/next after the fact is deleted, so the only reader action still on that interface is the two-finger cycle. Touch prev/next is the **pager**'s (below), and the KEYS keep their own path — app.ts's `stepLeft`/`stepRight`, which decide between navigating and ringing the margin bell at a dead edge. `gestures` does not import `nav`. **Pull to refresh (RDR11)**: `setPullRefresh(surface, run)` — called by `list.setup` with the list container and `() => refresh.refreshNow()` — adds a one-finger downward overscroll pull to the SAME state machine (a second machine could not axis-lock against this one). It engages only while the document is at the top (`window.scrollY <= 2`) on a touch that STARTED inside the registered surface, which is the whole gating story: the filter picker and the image lightbox are elements laid OVER the list, and the reader hides the list container, so one containment test buys exactly the exclusion the keymap spells out as `picker.isOpen()`/`lightbox.isOpen()` — without importing either (this module imports nothing, which is why the action is registered rather than called directly, and why the pull's state is module-level: there is no gesture instance to hang it on). **Axis lock, three faces**: a gesture that passes the slop horizontally is the swipe's for good and can never become a pull; an engaged pull `preventDefault`s every subsequent move (this, plus `overscroll-behavior-y: contain` scoped to the list surface in styles.css, is what stops Chrome Android running its OWN pull-to-reload on the same finger); and `pullEnd()` reports "this WAS a pull" so touchend skips the horizontal branches entirely. A second finger, 3+ fingers and `touchcancel` all drop it, and the two-finger→one-finger re-seed passes a null target so a gesture that began with two fingers never becomes a pull. The affordance is a lazily built `.srr-pull` badge (the lightbox's build-in-JS precedent — no index.html entry, no design.html drift-guard entry) that tracks the thumb at half distance, flips/accents past the threshold and parks as a spinner for at least `PULL_MIN_MS` while the cycle runs; a freshness token means a settling cycle can't clear an affordance a re-registration has replaced. `refreshNow()` carries app.ts's `guardBg` mutex inside it, so this is a new TRIGGER and never a second concurrency path. **Row swipe actions (RDR14)**: `setRowSwipe(surface, spec)` — called by `list.setup` with the list container — is the pull's mirror image in the SAME machine, for a one-finger HORIZONTAL drag that starts on a row (→ ★ Saved, ← read; the meaning is entirely the surface's). `spec` is `{row(target), move(row, dx, armed), end(row, dir)}`: this module owns the geometry (which axis, how far, armed past the exported `ROW_SWIPE_TRIGGER` = 64px) and never touches a row, so the affordance and the actions stay in list.ts — and a direction the surface can't act on simply doesn't paint, which is how availability is expressed without teaching gestures what a feed is. Gating is the pull's one containment test (start inside the registered, visible surface ⇒ not the picker, not the lightbox, not the reader), and `spec.row` returning null excludes the surface's non-row chrome (the "N new" pill, dividers, termini, the empty state). Its axis lock is the pull's three faces pointed the other way: a gesture that commits to the VERTICAL axis can never become a row swipe (it is a scroll, or at the top the pull), an engaged swipe `preventDefault`s every move so the list can't scroll under a dragged row, and `rowEnd()` reports "this WAS a row swipe" so `touchend` never also evaluates it as a reader page turn (the pager's own containment test excludes the list anyway — the lock belongs beside the other two faces, not on a guard in another module). The two machines are mutually exclusive by construction: the pull vetoes itself at `dx >= |dy|` and the swipe engages only at `|dx| > |dy|`, both measured against the ONE shared `AXIS_SLOP` — a different slop on each side would leave a band of gestures both machines claim. `armed` (and therefore the commit direction) comes from the last MOVE, not the lift, so what the affordance showed is always what commits. **Reader pager** (spec `docs/superpowers/specs/2026-07-27-reader-swipe-pager-design.md`, its tunings amended by `2026-07-27-reader-pager-carousel-design.md`): `setPager(surface, spec)` — registered by `pager.setup` with the reader `<article>` (`el.article`) — is the machine's FOURTH client, the row swipe's shape pointed at the reader, for a one-finger horizontal drag that pages prev/next with the article tracking the finger. `spec` is `{engage(side), move(dx), end(dx, commit, vx), cancel()}`: the geometry is this module's, the DOM and the meaning are `pager.ts`'s. `engage` answers with the drag's MODE — `"page"` (a live neighbor to track toward), `"resist"` (the dead edge: the damped drag, not the bell) or **`"skip"`**, which declines the drag outright when a prior commit is still animating/loading; a skipped drag never sees `move`/`end`/`cancel`, so nothing can arm state behind a commit in flight. Gating is the pull's one containment test (start inside the registered, visible surface — `el.article` is `hidden` on the list, so the list, the picker and the lightbox are all excluded). That test makes the surface's BOX the reachable area, which is why `.srr-reader` carries a **`min-height`** in styles.css (the viewport minus the page's own vertical chrome): an `<article>` sized to its content leaves a SHORT article a dead band underneath where the drag does nothing — a hole the blind swipe it replaced did not have, since that one read the whole document. It is a gesture property, not decoration; the browser suite pins the computed value. Gating adds the **horizontal-scrollable veto** (`inHScrollable`: any element between the target and the surface with real horizontal overflow — `scrollWidth > clientWidth + 1`, a wide `<pre>`, a table — keeps the gesture for its own scrolling). That veto also fixes a **pre-existing bug** — the old blind swipe fired prev/next off a code-block pan — and its intended behavioral delta is that a drag the pager declines now navigates nowhere at all, rather than paging after the fact. Axis lock, the same three faces (vertical-dominant past the shared `AXIS_SLOP` vetoes for the gesture's life; an engaged drag `preventDefault`s every move; `pagerEnd()` runs LAST in `touchend` because nothing follows it — the blind swipe it used to guard is gone). **The commit rule is this module's alone**: `"page"` mode AND travel in the engaged direction AND (`|dx|` past `PAGE_COMMIT_FRACTION` (**0.20**) of the SURFACE's own width — `clientWidth`, falling back to `window.innerWidth` where jsdom reports 0 — OR a **flick**: `|vx| >= PAGE_FLICK_VX` (0.5 px/ms) measured over the LAST move segment and required to point the same way as the drag, so a fast drag that stops before the lift reads as a considered release, not a flick). The fraction is 0.20 and no longer 0.25 because a quarter of a 390 px phone is ~98 px — a long pull for a thumb pivoting from the screen edge. **`end` carries the release velocity** (`end(dx, commit, vx)`, the same last-segment `pagerVx` the flick test reads): the geometry measured it, and the surface turns it into the settle duration, so a flick lands crisply where a considered release eases — one number crossing the seam rather than a second velocity tracker in `pager.ts`. **An ACTIVE drag whose travel crosses back through the origin re-engages the OPPOSITE side** (`wantSide !== pagerSide` in `pagerMove`) instead of clamping at 0: a reversed finger is asking for the other neighbour, and `engage()` is what owns re-deriving the side, the dead-edge mode and the preview — so a `"skip"` answer on reversal ends the gesture exactly as it does at first engage. It cannot leak into the other three clients: they are separate machines over the same touch stream, none reads `pagerSide`, and the shared `AXIS_SLOP` is untouched — a drag that reverses here was horizontal-dominant from its first move past the slop, so the pull had already vetoed itself and the row swipe had already claimed or declined it.

## `pager.ts`

The **DOM half of the reader swipe pager** (spec `docs/superpowers/specs/2026-07-27-reader-pager-carousel-design.md`, which supersedes the preview half of the v4.12.0 swipe-pager spec): what the drag LOOKS like and what a commit DOES, over `gestures.ts`'s geometry. Imports `{article-view, data, els, fmt, gestures, nav}` and **never `app` or `reader`** — the committed step arrives as the injected `PagerDeps.commit(side)`, list.ts's registration precedent. The preview is a **full article PAGE** (`.srr-pager-page`: a fixed, opaque, full-viewport clip box holding a real `.srr-reader` subtree built from the SAME classes `index.html` declares), lazily built in JS onto `<body>` (the lightbox/pull-badge precedent: no `index.html` skeleton, no `design.html` drift-guard entry). **Reusing the reader's own classes is the load-bearing decision of the whole feature**: identical typography, measure and line-breaking BY CONSTRUCTION, which is what lets the commit swap one surface for the other invisibly — a parallel skin would drift, and the drift would show up as exactly the jump this replaced (so `styles.css` restates html's own page padding on the box, restates `.srr-container`'s column on the inner `.srr-reader`, resets that element's gesture-surface `min-height` to 0 inside the clip box, and re-pairs the padding under the ≤500px block; a different measure or top offset re-breaks every line of prose across the handoff). It carries `aria-hidden` **and `inert`**: it previews while the committed article announces itself, but the masthead row is an `<a href>` and the article's own prose brings links, so `aria-hidden` alone left a focusable invisible subtree — an `aria-hidden-focus` violation, the rule class the a11y e2e layer enforces on every other surface. `inert` takes the whole subtree out of the tab order and out of hit-testing in one declaration, which is why it is there rather than a `tabindex` on each node the fill might produce. **Media inside it is INERT** (`article-view`'s `buildContent({inert: true})` → `.srr-media-stub`), and that — not the absence of content — is now what keeps FEB2's `querySelectorAll("audio,video")` index pairing and `player.ts`'s single capture-phase document `play` claim out of a second surface, stops a page you may abandon opening a second media stream, and stops a drag back toward a playing episode ghosting the node that currently lives in `.srr-player-media`; images stay REAL (`prefetch.ts` already warmed them, and they are the article's visual substance). `e2e/browser/pager.e2e.test.ts` is the guard on that renegotiation in real Chrome — exactly ONE `<audio>` in the document mid-drag toward a playing episode, and the player's node identity surviving the commit — which no other layer can give (jsdom implements neither `play()` nor `pause()`). A **cold neighbour** degrades to the masthead from `data.loadMeta` plus `.srr-pager-skeleton` bars, filled in when the article lands: today's masthead-only pane is the DEGRADED path now, not the design. While the finger is down `el.article` carries an inline `translateX` under `transition: none` (the pull's `srr-pull-live` precedent) with the page tracking it in from the edge, clamped to the engaged direction — which now says only that the article never drags the wrong way WITHIN a side, since a finger crossing back through the origin re-engages the opposite side in `gestures.ts` and the preview refills for the other neighbour; at a dead edge the **resistance** replaces the touch path's bell — `PAGE_RESIST` 0.3 of the finger capped at `RESIST_MAX` 64px, so the wall is FELT rather than announced after the fact (`bumpReaderEdge` now fires from keys alone). **On commit the outgoing article slides fully off and the preview lands at center OPAQUE AND COVERING — and stays there** while the guarded step renders the real article and `scrollTo(0, 0)`s it UNDERNEATH; `rest()` then clears the transform and removes the page in one synchronous block, and because both surfaces show the same content at the same geometry that removal is invisible. That is why there is no blank window and no visible scroll jump: a slow load now holds a correct-looking page longer instead of showing a floating title over nothing, and splitting `rest()`'s two acts across a task boundary in either order is precisely what a blink looks like. **The slide runs to the END before the step is asked for anything** (the second on-device feel-pass finding, after the truncated settle): the step re-renders and re-scrolls `el.article`, which stays VISIBLE — sliding out beside the incoming cover — until the cover is at center, so the earlier concurrent shape let the warm-step norm (the preview fill already warmed the article, nav's probes are cached) swap the OUTGOING article's content to the incoming one in plain view, mid-slide. Sequenced, the cover lands first (a timer at `dur + SETTLE_CLOSE_PAD_MS`), the step renders underneath a page that now fully covers it, and `rest()` follows the step's resolution — which also retires the interim settle HOLD (waiting out the slide after a fast step), since the step now starts after the slide by construction. A new drag mid-slide cannot be handed the surface synchronously — nothing is rendered underneath yet — so `engage` answers `"skip"`, but first calls **`hurry`**: it drops the transitions (the cover lands NOW) so the step renders and rests within a task or two. `gestures.ts` treats that `"skip"` as a decline-FOR-NOW — the gesture stays eligible and each later move retries engage — so a quick follow-up flick claims the surface the moment it rests instead of being eaten for the gesture's life (the reversal's skip still ends the gesture: mid-drag no commit can be in flight). `setup()` bumps a registration token (`gen`) BEFORE releasing a pending slide, so a stale `commitStep` continuation sees a foreign generation and bails instead of stepping the new deps or writing transforms onto the fresh surface. Under reduced motion nothing slides, so nothing waits and the step is asked at once. **`commit`'s `false` is the snap-back signal** — app.ts's "the cursor moved" answer, one signal covering both a busy mutex and a failed load — as is a throw. A commit is additionally raced against a **watchdog** (`COMMIT_WAIT_MS` 15s, comfortably under app.ts's `BUSY_STUCK_MS` 60s — that relationship is the point, not the number): while it waits, `el.article` is parked fully off-screen and `rest()`/`settleBack()` are its only writers anywhere in the frontend, so a repaint in that window would paint into an invisible surface, and giving the surface back before the stale-mutex reclaim becomes possible closes the class. Its guarantee is **strengthened, not replaced**, by the covering preview: while the watchdog waits the viewport now shows a correct page rather than sitting bare. The watchdog answers with its own `STALLED` sentinel rather than a second `false`, because the two snap back identically but leave the ENTRY TRANSITION in opposite states: a `false` step has SETTLED (app.ts's finally already cleared the flag), while `STALLED` is still in flight with "slide" armed — so that branch alone calls **`PagerDeps.abandon`**, handing the flag back so the late arrival fades in like any keyboard step instead of swapping with no transition at all. A `committing` flag is what makes a drag arriving meanwhile `engage` → `"skip"`, and a fill freshness token (`fillTok`, the `tok` idiom) stops a late meta card or a late article painting over a newer drag's page — or over a reversal (a probe blip just leaves the skeleton; the commit still renders the real article through the normal path). **Settles are velocity-CARRIED**, not the old fixed 200 ms: `settleDuration(dist, vx)` = `|dist| / max(|vx|, 0.1)` clamped to [`SETTLE_MIN_MS` 120, `SETTLE_MAX_MS` 260] on `cubic-bezier(0.2, 0, 0, 1)`, so the animation CONTINUES the drag at the pace the finger was already going instead of performing a separate act on it — one duration for both a flick and a slow deliberate lift was the last rubbery tell in this gesture. `dist` is whatever is LEFT: a surface width minus `|lastDx|` on the commit, the offset itself on the snap-back; `lastDx` is recorded by `move()` (in BOTH branches, so a dead-edge resist settles from its damped offset) rather than by `end()`, because `cancel` reaches `settleBack` carrying no offset at all and a cancelled drag still has the distance it travelled to settle over. **The 0.1 px/ms floor is load-bearing, not a rounding nicety**: a dead-stop release — holding still for a moment before lifting, which is what a careful gesture looks like — arrives with `vx ≈ 0`, and the unfloored quotient is `Infinity` (or `NaN` in the 0/0 no-travel case, which `Math.max`/`Math.min` propagate straight through the clamp into the style string and into `setTimeout`), which would arm the settle timer forever and leave an OPAQUE full-viewport preview parked over the reader. Settles stay closed by a TIMER rather than `transitionend` (jsdom never fires it, and a mid-flight rebuild detaches the node) with the pad now riding the COMPUTED duration (`SETTLE_CLOSE_PAD_MS` 50, so a 120 ms flick-back tears down at 170 ms instead of waiting out the old worst case), and a new gesture cycle clears the previous one's pending timer rather than racing it; under `prefers-reduced-motion` the settle is **instant** — the drag still tracked the finger (direct manipulation), but nothing moves on its own after the lift. **Teardown runs on EVERY exit path** — `rest`, the `settleBack` timer (through `rest`), `cancel`, and `setup()`'s re-registration against a rebuilt surface, the one path no gesture can reach — because a leaked page is an opaque full-viewport element sitting over the reader, the highest-severity failure this design has.

## `picker.ts`

The **filter-picker overlay** (`setup(el, PickerHooks)`, `open()`, `close()`, `render()`, `isOpen()`, `renderStatus(box)`): a fixed full-viewport panel (`.srr-picker`, `--z-overlay`) with its own scroll — the list's window scroll survives untouched underneath — opened from the list toolbar's now-viewing readout and the reader toolbar's filter button. `open()` captures the opener for focus restore, renders, scrolls the overlay to the top, and focuses the container (no row painted pre-selected); `close()` hides and restores focus. It renders the filter rows — the `[ALL]` / "★ Saved" scope-chip pair (`.srr-picker-scope`: equal-width `.srr-scope-chip` outlined pills above the list — meta filters with no source chip; ★ Saved only when something is saved, `[ALL]` full-width alone until then; the active one wears the shared `srr-active` tint plus an accent-tinted border), tag groups and feeds with source-color chips, health-tinted labels (an unhealthy feed/tag tints its label by grade via `data-grade` — warn amber, crit accent — instead of a leading dot that shifted the title), and async unread-count fill — each count sits **inline right after the name** as an italic, slightly smaller "×N" phrase (`.srr-unread`; the row title is shrink-only flex so the count follows the ellipsized name, not the row's far edge; `[ALL]` carries the whole-store unread total, the sum over every listed feed, absent at zero like every row's count; the ★ Saved row's `.srr-saved-num` reads the same way). `PickerHooks` declares the two callbacks `app.ts` injects: `onSelect` (routed to `selectFilter` — close + re-filter the LIST) and `onClose`. Filter row clicks are delegated via `filterBox.addEventListener("click", …)`; tag collapse toggles are stopped before the pick handler, and while the header **Info** stats toggle (`.srr-picker-info`, `statsMode`, reset off on every `open()`) is pressed the same tap routes to `openRowInfo` instead of `onSelect`. The **feed/tag info dialog** (`.srr-info-dialog`, refs grabbed in `setup()`) is a top-level modal opened by those stats-mode taps: a feed row opens its detail card (its "Articles" row shows the **live** count `total_art − (xp ?? 0)` — expired excluded; its Content section also carries the storage/retention rows — "Stored content" = `cb`, "Stored assets" = `ab` hidden at 0, both via `fmt.formatBytes`, and "Retention" = `exp` in days or "Forever"); `[ALL]` opens the **store-wide card** and a tag header its member-scoped rollup (both via `buildGroupInfo(feeds, storeWide)`): inventory (feeds / live articles / async unread sum / plus tags + saved on the store card only), the storage rows summed across the group, and a health census of every member's `feedGrade` (Stale/Error rows only when nonzero); ★ Saved has no card and is inert in stats mode; `closeInfo` holds the active teardown so a re-open never stacks two. All cards are **reader-facing on purpose** — internal bookkeeping (feed ids, HTTP validators, dedup/pack state, processing recipes, generation/latest-pack names, search-index state) stays off them; the settings footer owns the search-index flag and the admin GUI is where operators look. Unread badge fill is freshness-token guarded, hiding fully-read rows/tags when unseen-only is on; when unseen-only is OFF (read items shown) the picker passes `includeEmpty` to `groupFeedsByTag` so feeds with no articles also appear. **RDR9 — the at-scale ergonomics**, all three local to this module: (1) a **type-to-filter** row search in the header (`.srr-picker-search-input`), matching a folded substring (`search.ts`'s `fold`, the one folding rule the article index already uses) against a `data-match` haystack stamped on each row at BUILD time (name + tag for a feed, the tag for a header, the label for a scope chip — never `textContent`, which grows an "×N" badge as `fillUnread` lands). It narrows by toggling `srr-qhidden` over the rows already in the DOM — **a visibility pass, never a re-render**, so the async badges survive a keystroke — composing with (not fighting) the unread-only mode's own `srr-hidden`; a matching tag header carries its whole group and force-expands it (`srr-qexpand`), the mount switcher is deliberately never filtered (it is the store axis, not a lane), and nothing matching shows a `role="status"` empty note. **Escape is progressive**: with a query up, the overlay's own bubble-phase handler clears the query and stops propagation — only an already-empty query reaches app.ts's document handler, which closes the overlay as before. A query never survives a close (a panel that came up narrowed reads as "my feeds are missing"). (2) **Scroll memory across opens** — `open()` restores the last offset instead of hard-resetting to 0, but only when `rowSignature()` (every row token in render order + the view mode) still matches the panel the offset was measured against; a store refresh that added a feed, a Show-read flip, or an offset taken while a query was narrowing all land at the top as before. Module state, NOT localStorage: it is a within-session convenience, and after a reload the row set is rebuilt from a store that may have moved. (3) **★ Favorites** — a pinned lane above the tag groups, fed by a per-store `srr-favorites` id list (`keys.ts` `favoritesKey(mid)` — a feed id only means something inside its own mount). A favorite renders in the lane **in addition to** its normal row rather than moving out of it (the tag groups mirror how feeds are FILED, and a header whose health tint / unread rollup describes members it no longer lists would be lying) — which is why `fillUnread` sums [ALL]'s total over DISTINCT feeds, the one place the duplicate row would double-count. Marking is a **third header row-mode** (`.srr-picker-fav`, `rowMode: "pick" | "info" | "fav"` — one variable, so the modes are mutually exclusive by construction and reset to "pick" on every `open()`): while pressed, a tap on a FEED row marks/unmarks it; tags and the scope chips are inert. A mode, not a per-row star, because it costs one control instead of one per row — the same idiom that replaced the per-row ⓘ buttons. `renderStatus(box)` builds the **settings menu's status footer** into a caller-owned node (rebuilt unconditionally — app.ts hands a fresh footer per menu open and the sync callback refills it live): a relative-time-only "Updated X ago" freshness line, amber flags (stale fetch, "Search unavailable while the index rebuilds", "Sync failed — …", "Refresh failed — …" from `refresh.lastRefreshError()`), quiet notes ("Optimizing for faster loading…", "Synced X ago", "Sync pending…" from `sync.state()`), and always the build's **version label** (`.srr-status-version`, "srr <SRR_VERSION>" — even on an empty store).

## `fmt.ts`

## `profile.ts`

Portable backup/restore engine: `exportProfile()` / `importProfile(json, opts)` over a **`v:2`** JSON blob bundling `srr-seen`/`srr-saved`/`srr-unread-only`/`srr-img-proxy` plus THREE ordering fields — the blob-level `ts` (unix seconds of the last local seen/saved mutation, 0 = never; a pref-only change deliberately never stamps it) and the two per-key maps `st` (seen — `srr-seen-ts`, stamped by `nav.ts` beside every seen write) and `sd` (saved — `srr-saved-ts`, stamped by `saved.ts` beside every save AND un-save); both are additive, so old builds ignore them without a version bump — never `srr-hash`. **One per-key seen rule shared by both import modes** (`mergeSeen`): a key stamped on BOTH sides merges LWW by `st` (the strictly newer stamp wins IN EITHER DIRECTION — this is what lets an explicit `markUnreadFrom` rewind propagate instead of being re-raised by max-merge; ties break to max); a key missing a stamp on either side keeps the legacy raise-only max, so implicit rewinds still cannot happen and v1/pre-upgrade blobs interop safely. Adopting an incoming value adopts its stamp verbatim (never re-stamped to now — the ordering belongs to the device that acted; an unstamped adopted value drops the local stamp). **The saved set merges through one shared body too** (`mergeSaved`, used by the home store and every peer substate), in two layers whose ORDER is the interop story: layer 1 is the pre-stamps `base` — sync mode takes the blob's array wholesale when its `ts` is strictly newer (un-saves propagate), merge mode unions local-order-first — and layer 2, **sync mode only and only against a blob that carries an `sd` map at all**, overrides each chron whose two stamps differ, the strictly newer winning in either direction (an absent stamp reads as 0). That is what makes a save on device A concurrent with an un-save on B converge to the newer INTENT instead of to whichever blob carried the newer `ts` (RDR18 — the old blob-level LWW lost one of them), and it makes two concurrent saves of DIFFERENT articles both survive. A blob with no `sd` never reaches layer 2, so v1 and old-build v2 blobs merge byte-for-byte as before. **Save ORDER coexists with per-key stamps** by staying the blob-level winner's: the merged queue is `base`'s order with non-members filtered out, then layer 2's additions appended in the OTHER side's order — so per-key stamps decide only WHO is in the queue while `ts` decides the SEQUENCE, and two devices merging the same pair of blobs compute the same queue (a `ts` tie keeps each device's own order, as before). An un-save leaves a **tombstone** stamp (that is what outranks a peer's older save); tombstones are bounded at `SAVED_TOMBSTONE_CAP` (1024, newest first, ties by chron so two devices holding the same union prune identically), members' stamps never. Merge mode is deliberately excluded from layer 2 — its base is already the union, so the only thing layer 2 could do there is DELETE, and a file restore must never delete; it still adopts incoming stamps, so a restored save can be un-saved later from anywhere. The modes then differ on the other axes: **merge** (default; always for v1 — a file restore) — prefs = opt-in, `ts` bumped only when the merge actually changed seen/saved; **sync** (`mode:"sync"` + v2 — a `sync.ts` pull, the one-reader hybrid) — never stamps `ts` locally, and `ts` itself is still last-write-wins (a strictly newer blob's value is taken, floored/validated; an older-or-tied blob leaves it, so `ts` converges to max(local, blob)). The ONLY path that can LOWER seen is a strictly newer per-key `st` — the explicit rewind. `importProfile` returns `{ok, error?, changed?}` — `changed` = seen/saved values actually mutated (a ts/st/sd-only convergence is not a change). Prefs stay opt-in-gated identically in both modes; `sync.ts` always passes `prefs:false` so preferences never teleport between devices. `profileTs()`/`touchProfile()` read/write the blob ordering field (`PROFILE_TS_KEY` = `srr-profile-ts`); `localSeen()`/`localSeenTs()`/`localSavedTs()` expose the parsed maps for `sync.ts`'s push trigger and flush guard — `localSavedTs()` returns the **pruned** view, byte-identical to what `exportProfile` publishes, since a stamp the trigger counts but the push never sends would re-fire every cycle. Consumed by `dropdown.ts`'s backup dialog (`setProfileImportHook` wires the post-import refresh, always merge mode) and by `sync.ts` — the sync transport pulls/pushes this same blob in sync mode, so the endpoint's content doubles as a restorable backup.

## `sync.ts`

**Cross-device sync** of the portable profile over one HTTP endpoint (anything answering GET = last-stored profile JSON or 404, PUT = store the body; `credentials:"include"`, so an access-cookie-protected route works). `srr serve` ships that endpoint first-party at `GET|PUT /sync/<name>` (RDR18 — see root `README.md` → Profile sync; it is loopback/`hostGuard`-bound, so the reader and `/sync/` must be routed under one hostname), and any KV worker or WebDAV file answering the same two verbs still works. Off by default: the URL lives in `SYNC_URL_KEY` (`srr-sync-url`), set via the settings menu's Sync row → `dropdown.showSyncDialog()` (saving a NEW url kicks `syncNow({manual:true})` so enabling sync seeds/merges with the endpoint immediately); no request until one is set. The model assumes **one reader on every device**, so every cycle — background and manual alike — is the same hybrid merge (`importProfile(…, {prefs:false, mode:"sync"})`): **seen merges per key by the `st` timestamps** (newer stamp wins in either direction — ordinary reading only ever raises a frontier, so progress still converges to the union of what the one person read anywhere, while an explicit `markUnreadFrom` rewind, being the freshest stamp, survives and propagates; keys without stamps on either side keep the legacy raise-only max, so old builds interop) and **saved merges per key by the `sd` stamps over a blob-level `ts` base** (RDR18 — the base still replaces the set wholesale from a strictly newer blob so un-saves propagate, and each chron whose stamps differ overrides it in either direction, so a save on one device concurrent with an un-save on another keeps both intents; `ts` still decides the queue ORDER). The push needs no guard (after the merge, local holds the newer-ordered or higher value per key and the per-key-newest saved plus the LWW-newest ts) and fires whenever the endpoint is actually **behind** — `seenBehind(localSeen(), localSeenTs(), remote.seen, remote.st)` (missing key / older per-key stamp — even at equal values, the ordering itself must propagate / lower unstamped value), `savedBehind(localSavedTs(), remote.sd)` (some chron carries a strictly newer local stamp — the `ts` comparison alone stopped being able to see the saved axis once it merged per key, since a device adopts the peer's newer `ts` while its own save is still unpublished), a newer local `ts`, or a 404 seeded when local holds any state — not just on the in-memory `dirty` flag (a reload loses it), so an endpoint transiently regressed by a stale tab's flush or an old-build device **self-heals** on any device's next cycle; the fleet converges to (per-key newest-stamped seen, per-key newest-stamped saved in the newest-`ts` order). `savedBehind` is deliberately in the flush TRIGGER but NOT its guard: local's `sd` is the pruned view, so it can legitimately hold fewer tombstones than the remote and a guard reading that as a regression would skip every flush. A v1 remote (pre-upgrade endpoint / old-build device) gets one legacy monotone merge (`mode:"merge"`) and always forces a push so the endpoint upgrades to v2. `syncNow(opts)` returns whether the pull CHANGED local seen/saved (a ts-only convergence returns false); `manual` only forces the push. `pushSoon()` (1s debounce, called from `nav.ts`'s mutation seams — `recordSeen`, `toggleSaved`, `markAllRead`, `markUnreadFrom`) doubles as the **`ts`-stamping seam**: `touchProfile()` runs unconditionally, even before a sync URL is configured, since the ordering field must track every mutation from the start. `flush()` fires a last-chance `keepalive` PUT on pagehide/hidden, guarded by the remembered remote snapshot when one was ever pulled (no time for the pre-push GET whose merge makes a normal push safe; even a mistaken regressive flush heals on the next cycle). Tab re-focus and `online` re-pull (60s throttle on attempts). `init(merged, status?)` wires the lifecycle after the first route: `merged` = app.ts's shared after-merge refresh — which re-anchors the list when the BOOT pull changed the profile (a browser page refresh is the manual sync; there is deliberately no button — see app.ts); `status` refills an open settings menu's footer after every cycle (so enabling sync confirms itself). `state()` → `{on, okAt, error}` for the settings menu's status footer. Imports only keys + profile (unit-testable without a pack server, like profile.ts).

The `.srr-save` star (key `b`, `refreshSaveButton`/`toggleSave`) reflects/toggles the current article's saved state — a local flip off the guard mutex (the list re-derives stars from the live set on return).

## `pane.ts` and the split-view chrome

The split pane's **width and visibility** — a leaf module beside `split.ts` (which owns the breakpoint) and `scroller.ts` (which owns the scrolling box), importing only `keys.ts`, so it unit-tests with no markup and no pack server. It writes ONE custom property: `--split-pane-open-w` on `<html>`, the width the pane is SET to, never zero, defaulted in `tokens.css` because nothing writes it before `restorePane()` runs (or at all, if storage is blocked). `styles.css` derives the second, `--split-pane-w` on `<body>` — the width the page RESERVES — and zeroes it under `body.srr-pane-hidden`, so hiding is one class toggle with no JS layout pass and every fixed bar follows for free (they all read that one property). Exports `PANE_DEFAULT_W`(380)/`PANE_MIN_W`(280)/`PANE_COLLAPSE_W`(240)/`PANE_MAX_W`(560), `clampPaneW`/`storedPaneW`/`setPaneW`/`isPaneHidden`/`setPaneHidden`/`togglePane`/`applyDragWidth`/`restorePane`, and `initPane(deps)` — which wires the rail's `.srr-pane-toggle` and the `role="separator"` grip and takes the app's one `onSettle` re-layout callback. The width clamps to `[280, min(560, viewport/2)]` on every READ, not just every write (a width stored on a 2560 monitor must not survive onto a 1280 laptop), and `clampPaneW` is TOTAL over its inputs because `Math.min/max` propagate NaN and a coordinate-less event would otherwise write the string `"NaNpx"`. Persisted globally in `srr-pane-w` / `srr-pane-hidden` — a property of this SCREEN, so deliberately outside the portable profile. `persist` is a per-call flag, not a policy: a drag calls the visibility/width path once per animation frame, and a version that always wrote would put a localStorage hit on every frame. `restorePane()` deliberately never persists — restoring through the writing paths would freeze today's `PANE_DEFAULT_W` into storage as a preference the user never expressed.

### The chrome it drives

Above the breakpoint the toolbar is a **full-width rail** cut into one grid segment per pane (`grid-template-columns: var(--split-pane-w) minmax(0, 1fr)`, no column-gap and no side padding). Track 1, `.srr-tb-pane`, IS the pane — it reads the same property the pane's own width reads, so the two cannot disagree by a pixel — and carries the pane toggle, the now-viewing readout and the filter funnel over the surface they act on rather than 700px away over one they don't touch; its `border-right` continues the pane's seam down through the rail. Track 2, `.srr-tb-reader`, is everything left of the window, which is exactly the box `.srr-container` centres in, so centring the back/prev/next/save group in it as ONE unit lands the accent next pill on the reading column's midline at any window width and any pane width. The two zeroes are load-bearing for DIFFERENT reasons and neither may be argued from the other: a column-gap really does take the group off that midline by half of it, while symmetric side padding would not — what zeroing the padding buys is the SEGMENT IDENTITY that every rule under this is written on (`pane.e2e.test.ts` pins `seg.left === 0`). Below the breakpoint both wrappers are `display: contents`, so every button is a direct grid item of the bar again and the phone templates place exactly what they always did (verified pixel-identical at 360/420/768/999 on both surfaces; the phone reader bar now NAMES its columns AND its row, because one filter button shared by two surfaces cannot be ordered for both by document order, and auto-placement's forward-only cursor would otherwise give the bar a second row). The **resize grip** (`.srr-pane-grip`) is the seam itself: a real ARIA window splitter (`role="separator"` + `aria-orientation` + `aria-label` + live `aria-valuemin/max/now`), 7px of hit area over the pane's own 1px border, transparent at rest and `--accent` on hover or while dragging. Pointer drags run under pointer capture at one write per animation frame, persisting and asking for the app's single re-layout only on release (rows genuinely re-wrap at a new width, but once, not sixty times a second); the keyboard drives it too — ←/→ step 16px, Shift 64px, Home/End to the floor/ceiling, double-click resets to the 380 default. It is focusable unconditionally, which is safe ONLY because the stylesheet `display: none`s it below the breakpoint: any merely-invisible treatment would leave a phantom tab stop on every phone. **Three doors hide the pane** — the rail's toggle button (`aria-expanded` over the region it names, its accessible name saying what the press will DO, "Hide list" / "Show list", since a sighted user reads the pane's presence off the layout and a screen-reader user cannot), the grip's Enter/Space, and the `L` key (surface-agnostic, so it sits beside `/` and `?` rather than in `KEY_ACTIONS`, whose list branch would swallow it; below the breakpoint it is a REFUSAL, not a no-op, because the stored flag is read back at ANY viewport and an accidental `l` on a phone would open the next desktop session with no list and nothing saying why) — plus a fourth that is not a press at all: a drag under `PANE_COLLAPSE_W` (240) collapses instead of clamping, leaving the stored WIDTH alone so re-opening restores the last real one. That fourth door is why the button's label syncs from the low-level `applyHidden` and not from the committed setter. A hidden pane keeps its real width and stays laid out, taken off screen by `visibility: hidden` + a transform — never `display: none`, which would destroy its `scrollTop` and force a re-measure and re-anchor on every show — so showing it again is a pure class removal with nothing to race; the transform also carries the pane's own fixed children (the arrivals pill) with it, since a transformed element is the containing block for its fixed descendants. The rail RESTATES its template in that state (`1fr auto 1fr`) rather than inheriting the collapse: at a zero reserve track 1 would crush the pane segment to 0px and spill its controls — the toggle that brings the list back among them — over the article, and the empty third track is what re-centres the reader group on the window, which at a zero reserve IS the reading column. Finally, `enterSearch` **un-hides**: the pinned search bar rides the pane AT THE PANE'S WIDTH, so over a hidden pane it is a 0px box (styles.css takes it off screen outright with the pane) — a live search mode with an input nobody can see, over results that are themselves hidden. That is a correctness rule, not a courtesy, and `enterSearch` is the one funnel both the `/` key and the settings-menu row go through.
